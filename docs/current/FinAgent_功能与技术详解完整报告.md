## 阅读说明

这份报告面向项目团队、比赛评审和后续开发者。它既解释使用者能做什么，也说明一句话怎样经过模型、规则、数据库和确认页面，最终变成可以追溯的业务结果。正文先讲清概念，再展开字段、算法、状态和失败处理；附录提供完整提示词、计划示例、接口索引和代码定位。

当前系统已经是一个具备结构化计划、确定性校验、逐笔页面确认、周期指令和请求轨迹的本地 AI Banking 演示系统。其核心价值是把语言理解与业务决定分开，同时让决定有记录、让执行有固定参数、让失败有明确去向。它仍属于模拟银行工程原型，未接入真实银行，尚未开展真实模型的系统性对照实验。

文中的“已经实现”以当前源码为依据，“已经验证”以保存的工程检查结果为依据，“建议”表示尚待实施。193项后端测试全部通过，说明这些测试覆盖的工程行为成立；它不等于模型在193条自然语言输入上均正确，也不等于真实转账系统已经达到生产标准。本次报告编写只读取代码与既有证据，没有再次执行业务实验或调用真实模型。

代码主要位于 D:/finagent。最新规则版本为 finagent-ns-1.1，消费统计口径版本为 spending-v1。阅读时可将“模型计划”理解为待检查的草稿，将“操作单”理解为参数已经固定的业务申请，将“回执”理解为事务提交后的实际结果。三者的权限和可信度不同。

## 1 项目定位与已经实现的功能

### 1.1 项目实际解决的问题

用户习惯说“查余额，然后从活期转100元给张三”，系统接口却需要明确的账户编号、收款人编号、整数分金额和确定的执行次序。如果直接让语言模型调用扣款接口，一次误解就可能变成错误交易；如果完全依靠关键词模板，又很难覆盖自然语言的变体和组合需求。

FinAgent 采用两者结合的方式。语言模型负责把中文变成有字段和依赖关系的 Plan；后端再检查这份草稿是否完整、是否保留条件、对象是否属于当前用户、金额是否有原文依据。可以准备业务时，系统展示操作单，由使用者在页面确认。真正改变余额或卡片状态的代码处于数据库事务内，还会重新检查条件和资源状态。

因此，系统不是只回答银行知识问题的聊天机器人。它能查询演示账本，也能准备并提交模拟业务，有持久化任务、业务回执和审计事件。另一方面，它不是自主扣款代理：聊天语言不能取代页面确认，模型也没有执行或确认工具。

### 1.2 功能矩阵

| 能力 | 当前可以做什么 | 关键边界 |
| --- | --- | --- |
| 账户查询 | 查看本人账户、名称、尾号、余额和状态 | 身份来自服务端会话 |
| 收款人查询 | 查找本人预置收款人，辅助解决同名歧义 | 不支持任意陌生人的直接转账 |
| 单笔转账 | 本人账户互转，或转给预置收款人 | CNY，单笔最多5000元，演示日累计最多10000元 |
| 消费统计 | 按时间、账户、类别计算消费与退款净额 | 账本计算，不让模型计算余额 |
| 流水查询 | 按支持的范围查询交易证据 | 查询范围受接口和 Plan 能力限制 |
| 消费比较 | 既有统计接口和页面支持上期对应区间、上月整月、自定义比较 | 新 Plan 编译默认 comparison_mode=none，不能把底层全部能力等同于模型计划能力 |
| 卡片管理 | 查询卡片，准备冻结或解冻并页面确认 | 未实现开卡、调额、正式挂失等完整业务 |
| 条件转账 | 消费净额严格大于或小于阈值时才准备转账 | 不支持任意条件、复杂分支和条件公式 |
| 多任务计划 | 保存最多12步，按依赖处理读与写 | 写步骤逐笔暂停并确认 |
| 周期转账 | 创建每月指定日的长期指令，暂停、恢复、确认取消 | 每期生成普通操作单，仍需页面确认 |
| 手动日历 | 推进演示日期，检查到期指令和过期行为 | 本地 manual 模式专用 |
| Trace | 展示计划、规则、追问、修复、错误、时间与耗时 | 调试证据，不是模型内部思维过程 |
| 情绪识别 | neutral、urgent、frustrated、distressed及置信度与原文证据 | 只识别和展示，没有情绪风控或干预策略 |

额度是该演示工程中写死的业务配置，不代表真实银行法规或真实产品额度。应用中的账户、收款人和交易均属于演示数据。本文对额度的解释是代码行为说明。

### 1.3 三类核心场景如何覆盖比赛要求

比赛截图中的人工智能赛道要求至少覆盖三个核心场景，当前代码可用于展示智能转账、账单分析和卡片管理。新版增加了这些场景的共同基础：计划结构、条件保留、执行确认、周期管理和可审计轨迹。

“账单分析”当前有类别统计、净消费和明细证据等能力，但没有训练并验证独立异常检测模型，也没有完整的年度报告生成器。“卡片管理”目前集中在冻结和解冻，不能将这两个动作描述成整套银行卡全生命周期服务。理财推荐和申赎、AA拆分、订阅代扣、购买鲜花蛋糕等跨机构服务，均未进入当前可执行白名单。

### 1.4 四种运行组合

项目保留 live 与 mock 两种模式，也保留 model 与 legacy 两种计划选项。live加model是本次神经符号主通道；live加legacy是旧模型工具选择路径；mock用于不调用真实模型的模板演示和回归。需要注意，mock并不意味着所有输入都走新版模型计划：旧单场景仍可走原模板，周期或已有 neuro_plan 等情况才会进入新版计划接线。

这使旧路径可以作为回归基础和将来的对照基线。不同组合的自然语言覆盖范围不同，不能只看页面长得相同就认为后台模型相同。任务的 mode在创建时保存；切换环境变量或启动方式后，建议建立新任务来避免混用旧上下文。

## 2 神经符号的含义与职责分配

### 2.1 用一个生活类比解释

可以把模型看成接待员，把 Plan 看成申请表，把验证器看成业务审核员，把操作单看成待签字的正式申请，把执行事务看成办理柜台。接待员擅长理解不同说法，但不应自己批准额度、不应选择客户没说过的账户，更不应代客户签字。

神经部分使用大语言模型理解语言变体和任务组合；符号部分使用显式数据类型、规则函数、状态机、参数摘要和数据库约束做确定性判断。给定相同的结构化输入、资源状态、时间和规则版本，规则代码具有确定的处理结果。模型输出则仍可能随模型版本和请求发生变化。

### 2.2 各层负责什么

| 层 | 输入 | 输出 | 主要责任 |
| --- | --- | --- | --- |
| 对话层 | 用户原文与当前任务 | 本轮请求和上下文 | 保留消息与当前未完成需求 |
| 理解层 | 原文、目录、Schema | 候选 Plan和情绪字段 | 翻译语义，不批准业务 |
| 结构检查层 | 候选 Plan | 合法类型或违规报告 | 工具、字段、依赖、时间结构 |
| 语义依据层 | Plan与用户消息 | 纠正或语义错误 | 金额、对象、周期不能凭空产生 |
| 落地层 | 语义名称、元金额、时间表达 | 资源ID、整数分、日期范围 | 用当前数据库与Clock解析 |
| 规则层 | 动作、参数、业务上下文 | 批准、证书、违规或追问 | 条件、余额、快照和R10 |
| 准备层 | 已校验业务参数 | 固定操作单 | 保留摘要、快照、有效期 |
| 授权层 | 页面确认凭据 | 有效确认请求 | 用户主动批准具体申请 |
| 执行层 | 已授权固定操作单 | 账本变化与回执 | 事务、幂等与最终复核 |

这不是把所有判断都交给一个“聪明提示词”。提示词是生成约束的一部分，服务端必须独立验证。同样，规则层并不理解所有自然语言：当前系统的语义依据检查还使用若干关键词和正则，其覆盖范围有明确局限。

### 2.3 为什么要有中间表示

如果模型只输出一句“可以转账”，后端无法知道它理解的对象、金额、条件和顺序。结构化 Plan 把这些信息显式化，使它们可以逐字段检查、保存、比较、修复和执行。

Plan 是类似抽象语法树的受限业务中间表示，但它还带有步骤依赖图。它不是任意Python程序，不允许用户或模型提交代码，也不接受自由逻辑表达式。有限的语言表达能力换来更清晰的执行边界：无法表示的要求应澄清或拒绝，而不是猜一个近似操作。

### 2.4 理解正确和执行安全是两个问题

Schema通过只能证明字段符合结构，不能证明模型理解了用户。例如用户要转100元，模型写了500元，两者都可能符合金额字段类型；因此需要语义依据检查。即便模型理解正确，用户确认前账户又发生变化，原计划也可能不再有效；因此确认事务还要重验快照和余额。

这些检查互补。不能因为存在页面确认就不做语义校验，也不能因为准备阶段已经校验就省略确认阶段复核。系统安全是多个机制共同作用的结果，单个规则或一张证书无法覆盖所有风险。

## 3 整体架构与模块关系

### 3.1 从前端到数据库

前端使用React与TypeScript，Vite承担开发服务和构建。后端使用FastAPI提供HTTP接口，Pydantic定义输入模型，SQLAlchemy操作SQLite。真实语言理解通过兼容聊天补全与工具调用的模型接口完成。项目主要以本地单进程API方式运行。

核心调用关系可概括为：

```text
React 对话页面
  -> FastAPI /api/tasks 或消息接口
  -> agent.service 对话路由
  -> tracing.traced_send 包裹请求
  -> planning.engine.send
       -> payload_for 组装上下文
       -> temporal.resolve 建立用户时间依据
       -> provider.generate 生成与最多两轮修复
       -> schema.validate_asset 和 semantic_check
       -> R10 追问或 compile_step
       -> 持久化 AgentStep
       -> engine.run 逐步处理
            -> verifier.verify 与 record
            -> registry.execute
            -> domain.operations.prepare
  -> 页面操作单
  -> confirmation-token 接口
  -> confirm_proposal 确认事务
  -> ledger 账本 与 BusinessResult 回执
  -> resume_after_confirm 继续剩余步骤
```

图中的R10不属于大模型第二次聊天生成，而是后端直接产生的确定性业务追问。时钟推进和周期调度属于另一条入口，最后仍接入同一个业务准备与确认管线。

### 3.2 核心模块的边界

planning/schema.py管结构，provider.py管模型请求，engine.py管计划的落地与执行。temporal.py负责从当前用户消息建立时间依据并纠正模型周期字段。verifier模块负责规则注册、结果和证书；standing.py负责长期指令；tracing.py负责记录一轮请求的结果。

旧registry依然是工具白名单和调用分发的统一入口。旧domain/operations.py依然管理固定操作单和确认事务，ledger.py依然负责账本写入。新版并没有另建一套直接扣款代码，因此新旧理解路径最终共享资金和授权机制。

### 3.3 三种数据要分清

对话数据包括AgentTask、AgentMessage和AgentStep，回答“用户说了什么、计划怎样变化、哪一步处理了什么”。业务数据包括账户、流水、Proposal、TransferOrder和BusinessResult，回答“业务参数是什么、是否真正提交、余额怎样变化”。验证与诊断数据包括VerificationRecord、TraceRecord和AuditEvent，回答“为什么允许、为什么拒绝、模型是否报错”。

长期指令又有自己的订单、确认请求和月度发生记录。长期指令代表反复准备业务的要求；每期操作单代表一次具体申请；转账订单代表已经提交的模拟转账。这些对象不能合并成一个笼统的“任务成功”。

## 4 一次请求的完整生命周期

### 4.1 入口与身份

用户先选择演示身份，后端建立演示会话并设置Cookie。后续查询和写请求从Cookie解析会话，再确定owner_id和dataset_version。模型的输入中可以看到账户名称和尾号，但不能通过写一个owner_id切换身份。

写请求还需要同源来源和CSRF令牌。通过后，聊天文本存入AgentMessage。对话任务持久化，因此刷新页面可以从服务端恢复状态，而不只依赖浏览器里的一份临时消息数组。

### 4.2 组装模型能看到的上下文

payload_for提供当前Clock时间、上海时区、本轮input、active_dialogue、最近16条history、账户收款人卡片目录、当前会话已有操作任务和pending_plan。active_dialogue是当前未完成请求的对话，依据current_request_start筛选；history用于指代理解，不能自动带回已经完成请求的授权。

目录让模型知道可以使用哪些语义名称，但最终匹配仍由后端执行。pending_plan只是上一份候选资产，可能有错，也可能包含已过时的追问。助手说过“每月1号可以吗”不是用户主动要求每月转账的证据。

### 4.3 模型输出和结构检查

新版live强制模型调用plan_request。收到返回后，服务端检查是否恰好有一个正确名称的工具调用，解析arguments为JSON，再进入Pydantic和依赖图校验。普通自由文本不会直接进入业务执行。

无效Plan进入定向修复：后端把规则编号、字段路径、观测值、预期值、提示和前一份资产发回模型。第一次生成后最多再修复两轮。网络、认证和HTTP请求格式错误走另一条分支，不会被当成“用户没说清楚”反复修复。

### 4.4 时间依据与完整性

当前后端先从用户消息建立周期依据，再用这份依据纠正模型的recurrence。用户没说每月，模型却填monthly时，会清除该字段；用户说每月但没说几号，模型擅自填1号时，会改回null。校验通过后，R10决定是否需要默认日期确认。

如果R10触发，系统保存追问记录，返回gathering_info，不编译执行步骤、不生成转账操作单。用户补充或明确接受默认日期后，再继续处理账户、收款人、金额等缺失信息。

### 4.5 落地并处理计划

信息足够时，compile_step把名称和尾号匹配为当前用户的资源ID，把元金额变为整数分，把结构化时间变成查询区间，把消费条件编译成后端可计算的固定条件。整个Plan的步骤编译完成后才创建新版本的AgentStep。

执行器按拓扑序处理步骤。只读查询可以立即完成；准备写操作时先做规则检查，再调用既有prepare函数生成操作单。返回awaiting_confirmation后停止，等待页面确认。长期指令则返回长期确认摘要，等待激活。

### 4.6 确认和继续

使用者点击确认，页面先请求与该操作单绑定的确认令牌，再提交confirm。后端确认事务重新验证会话、状态、有效期、令牌、参数摘要、消费条件、资源快照、余额和额度，成功后更新账本与回执。

确认接口随后调用resume_after_confirm。上一写步骤只有在操作单状态为executed时才标记成功，然后继续后续依赖步骤。下一笔写操作会生成新的操作单，不能沿用上一笔的确认来自动执行。

### 4.7 请求结束后的轨迹

traced_send在一轮请求结束时收集该轮新增验证记录和当前计划，将Trace写入数据库并输出日志。Trace标识返回给前端。它记录候选计划、规则结果和异常，不记录模型隐藏推理，也不代表将来确认事务已经完成。

## 5 Plan 的类型与结构约束

### 5.1 顶层字段

| 字段 | 类型与范围 | 含义 |
| --- | --- | --- |
| steps | Step数组，最多12项 | 需要处理的工作步骤 |
| recurrence | TimeExpression或null | 整体周期要求 |
| emotion | Emotion对象 | 情绪识别与原文依据 |
| clarification | 最多1000字符或null | 非时间信息缺失时的模型问题 |

执行资产至少有一个步骤。澄清资产允许steps为空，但clarification必须非空且不是纯空格。这样模型可以合理地询问信息，不必为了凑结构编造一个转账步骤。纯空计划既没有动作也没有问题，会被拒绝。

Pydantic统一设置extra=forbid和strict=True。未知字段不会被静默忽略；类型也不随意转换。例如把字符串当整数日期、把额外start字段塞进时间表达，均不能直接通过。这能防止结构看似正确但后端忽略了一部分参数。

### 5.2 Step 字段

每步包含唯一id、tool、params、depends_on、可选condition、可选recurrence和on_failure。id长度为1至60字符，依赖引用步骤id。on_failure只能是stop或continue_independent_readonly。

工具集合为list_accounts、list_transactions、summarize_spending、list_recipients、list_cards、prepare_transfer、prepare_card_action、get_task_status。没有execute_transfer或confirm工具；这不是提示词中一句“不要执行”，而是结构上没有给模型这样的动作入口。

### 5.3 Params 是语义参数而非数据库命令

Params允许source、target、amount_yuan、category、account、card、action、time、q和task_id。转账使用source和target等语义名称，而不是允许模型直接提交owner_id或任意账户ID。分类限制为餐饮、购物、交通、未分类、全部。卡动作只允许freeze或unfreeze。

amount_yuan是十进制字符串，结构限定最多两位小数。这个字段表达用户的元金额；底层接口使用amount_minor整数分。task_id是例外的资源引用，但必须来自当前用户当前会话已有业务任务，后端会复查归属和数据版本。

每个工具还有自己的参数允许集合。即便Params定义中存在category，也不意味着list_accounts能接收category。semantic_check检查“该工具实际收到哪些非空参数”，若超出工具能力会报P_TOOL_PARAMS，而不是悄悄丢掉。

### 5.4 时间类型

TimeExpression共有type、unit、n、period、freq和day。type只允许offset、period、recurring。offset要求unit为day或month且n为整数；period要求给定受支持枚举；recurring要求freq=monthly，day可以暂缺或为1至31。

它是共用模型而不是任意字段拼接。结构校验检查类型对应的有效字段集合：offset不能同时携带monthly，period不能塞一个day。n的范围为-365至365；这里只是字段上限，不代表所有这样的大跨度查询都具有完整数据。

### 5.5 条件类型

Condition只允许step_ref、field、op和value。field固定为net_minor，op为gt或lt，value为用户阈值的元金额字符串。条件只能用于转账，引用步骤必须是其祖先summarize_spending。

这意味着“消费超过500元”可表示；“工资到账以后”“余额足够且每周五并且天气好”“至少500元否则转200元”等不属于当前条件语言。系统应该明确澄清，不能把这些条件删掉变成无条件业务。

### 5.6 依赖图检查

validate_asset建立id到步骤的索引，再通过深度优先搜索检查依赖：找不到依赖、重复id和循环均产生P_DAG。合法图被排成拓扑序，然后为每步计算祖先集合。准备写步骤必须有只读祖先；条件引用必须位于祖先链中。

当前“有前置读”的结构检查判断祖先里存在非prepare工具，并不在形式上证明该读步骤一定与写操作业务相关。提示词要求相关查询，底层落地和业务复核进一步检查资源，但“读写相关性”的更严格规则仍是后续可增强点。不要将现有P_READ_BEFORE_WRITE夸大成全语义依赖证明。

## 6 模型接口与受控生成

### 6.1 请求结构

request_plan使用MODEL_API_KEY、MODEL_BASE_URL和MODEL_NAME。当前代码默认模型名为deepseek-flash，具体运行可通过环境变量覆盖。请求关闭thinking，max_tokens为3500，HTTP超时30秒。它通过tool_choice指定唯一plan_request，并为工具Schema设置strict=true。

系统消息是当前PLAN_PROMPT，用户消息是序列化后的payload。修复时额外附上包含previous_plan和violations的反馈。没有在模型请求中发送页面确认令牌。HTTP调用由measured_post记录耗时及调用遥测，但遥测不自动成为模型效果证明。

### 6.2 为什么有两份 Schema

本地Plan类型包含完整约束；发送给供应商的wire Schema由strict_schema转换。转换会展开本地$defs引用，把const改为enum，删除default、title，以及字符串和数组的minLength、maxLength、minItems、maxItems等兼容性问题字段。对象统一additionalProperties=false，并将属性列为required。

这不意味着长度和步数约束取消了。供应商侧省略的约束仍由本地Pydantic与validate_asset执行。服务端需要支持可空字段，因为wire Schema的required表示字段必须出现，而不是所有业务槽位都必须有值。未提供的信息应当用null表达。

### 6.3 接口地址处理

对官方api.deepseek.com的根地址或/v1地址，代码会调整为/beta再拼/chat/completions，这是当前实现的strict工具通道兼容处理。自定义网关或非官方域名保留其配置路径。

这里描述的是当前代码的适配逻辑，不能保证任意网关都接受相同参数。若模型名、thinking字段、strict工具定义或地址不匹配，应以服务端HTTP错误和request_id排查，而不是让用户反复换一种说法。

### 6.4 生成结果如何处理

服务端要求返回恰好一个plan_request工具调用，再解析arguments。多个调用、错误工具名、JSON缺损或不合类型，会成为P_RESPONSE或P_SCHEMA等计划错误。合法澄清资产可以正常返回，不进入修复预算。

最大调用次数是初次加两次修复，共3次。并不是每次聊天都会调用3次，也不是HTTP400会自动重试3次。只有可修复的PlanInvalid进入该循环；接口故障直接进入错误或受限降级路径。

### 6.5 提示词的作用和局限

提示词主要要求忠实翻译当前请求、保留条件和顺序、使用白名单、不猜对象金额、输出结构化时间和情绪。时间追问的时机和默认1号建议已经从提示词转移到R10。提示词仍允许非时间信息的简短澄清，例如付款账户没提供或同名收款人不能确定。

这些要求可以提高生成质量，但不能仅凭“写进提示词”就认定模型必定遵守。后端的独立检查、归属匹配、时间纠正和确认事务，才使违反生成要求的候选资产有确定的处理路径。

## 7 用户语义依据与后端落地

### 7.1 语义依据检查解决什么问题

语义依据检查常称grounding。它问的不是“这个字段格式对不对”，而是“这个字段有没有来自当前用户需求的依据”。用户提到500元消费阈值和100元转账金额时，模型不能把500填进amount_yuan；目录里有两个张三时，模型不能自己挑其中一个。

当前semantic_check检查金额与转账子句、对象名称与尾号、时间范围、条件方向、任务覆盖和工具参数。其主要手段是受限字段对照和中文正则，工程上可解释且方便测试，但不等于完整自然语言蕴含判断。

### 7.2 金额依据

normalize_money支持常见中文数词与元、块、圆等表达。语义检查从转账子句提取金额，并支持“金额改成”等明确修订表达；单个转账步骤优先对照最新金额。模型金额还必须出现在用户数字依据集合中。

金额存在原文中并不充分，因此还需要子句绑定。例如500既可能是消费阈值，也可能是另一笔转账。现有检查通过P_AMOUNT_BINDING降低混淆风险，但更复杂的多句、否定、计算金额和嵌套指代仍需要新测试。用户“转余额的一半”目前不能让模型自行算出最终扣款金额。

### 7.3 对象依据和匹配

对象参数先检查名称或尾号在用户当前需求中是否出现，再由match从owner_id限定的账户、收款人或卡片集合中匹配。匹配允许确切名称、去掉“账户”的名称、尾号，以及名称加尾号。匹配结果必须唯一。

付款来源总是本人账户。目标先判断是否是本人账户，否则匹配本人保存的Recipient。缺少名称、找不到对象或存在多个候选时，会抛出Clarify。对象匹配不是向全互联网寻找同名人的服务，也没有使用向量检索自动补全陌生收款人。

### 7.4 参数编译

compile_step将Plan的语义参数变为registry的执行参数。prepare_transfer得到source_account_id、target结构、amount_minor和CNY；prepare_card_action得到card_id和动作；消费查询得到start、end、account_id、category等。

编译后的参数再次经过registry.validate。这样模型Plan和底层工具之间有一个确定性转换层，而不是把模型返回字典直接展开到扣款函数。相同名称在不同用户下会得到不同资源集合，不会共享一个未经归属过滤的ID表。

### 7.5 条件编译

消费条件引用前置summarize_spending的类别、账户和时间，编译为spending_gt或spending_lt、固定起止日期与threshold_minor。比较阈值通过精确金额转换，不接受模型自由表达式。

固定区间的意义是：确认的是这段具体范围的消费条件，而不是让“本月”在过了一天或跨月之后悄悄改变。确认事务重算的是操作单中已经固定的条件。查询和计划在新一轮请求中可随Clock变化，而同一操作单的已确认参数不能漂移。

## 8 计划依赖与逐步执行

### 8.1 拓扑顺序和执行状态

AgentStep保存plan_version、ordinal、tool_name、depends_on_json、args_json、result_json、result_ref、status和on_failure。数据库保存的是具体步骤和执行结果，不是只存一串模型文本。

典型状态有pending、running、succeeded、awaiting_confirmation、failed、skipped和cancelled。AgentTask记录整体状态，如gathering_info、running_readonly、awaiting_confirmation、completed和partially_completed。步骤状态比一句最终回复更可靠，因为能说明哪部分实际处理了。

### 8.2 写操作怎样暂停

run依次读取当前计划版本的步骤。遇到已经完成或跳过的步骤不重复处理。依赖没有成功的步骤被标记skipped。准备写操作返回proposal后，该步骤标记awaiting_confirmation，任务记住proposal_id并返回页面，不继续准备依赖它的后续写业务。

继续执行时，如果操作单已executed，才将写步骤标记成功并释放当前proposal关联；若仍待确认，执行器停住。多笔写计划由此形成“准备第一笔—确认第一笔—准备第二笔—确认第二笔”的流程。一个Plan不是一份对全部未来写操作的自动授权。

### 8.3 失败处理

默认on_failure=stop。某步抛出业务错误时，该步骤记录失败和error_code，其余pending步骤被跳过。continue_independent_readonly允许符合现有计划结构要求的独立只读步骤继续；依赖失败步骤的动作仍被跳过。

条件不满足可成为skipped而不是执行失败，表示明确没有发生写操作。任务的completed只表示计划处理结束，并不总等于每个业务动作都提交；应结合步骤状态、proposal状态和回执判断。因此比赛演示和实验评价必须记录实际业务结果，不能只统计completed字样。

### 8.4 并发响应与计划版本

模型调用发生在数据库写锁之外，避免等待远程服务时占用SQLite写事务。调用前记录任务修订时间；模型返回后进入atomic_write，重新载入任务和会话，检查任务是否已变化或被停止。如果旧响应已过时，就不接受它覆盖较新的用户请求。

新版计划接受后递增plan_version，并将新的步骤写入数据库。读取执行步骤时按版本过滤，避免把旧计划的某一步误当作新计划的一部分。这个机制针对应用请求级别的竞争，不代表当前SQLite部署具备分布式调度能力。


## 9 确定性验证器与证书

### 9.1 统一接口

验证器入口为verify(action, params, context)，返回VerifyResult。action是工具或业务动作，params是结构化参数，context提供数据库、owner_id、用户条件依据、操作单、情绪和周期目的地等检查信息。

VerifyResult包含approved、certificate、violations和would_block。Violation统一使用rule_id、field、observed、expected、hint。这个结构既可用于页面解释，也可供修复反馈和统计脚本读取，不必从一大段自然语言里重新猜失败原因。

### 9.2 当前规则

| 规则 | 默认模式 | 触发条件 | 结果 |
| --- | --- | --- | --- |
| R1 条件完整性 | enforce | 用户命中条件标记，准备写操作却没有条件结构 | 阻止生成无条件操作单 |
| R2 余额充足 | enforce | prepare_transfer的来源账户余额小于金额 | 拒绝准备或确认 |
| R3 资源快照一致 | enforce | 操作单中的账户、收款人或卡片版本与当前状态不一致 | 要求重新准备 |
| R4 周期只登记长期计划 | observe | 存在周期信息但目的地不是standing_orders | 记would_block，不单独拦截 |
| R10 周期字段完整性 | clarify | 有用户周期依据，monthly且day为空 | 返回后端日期问题，不执行工具 |

R10使用独立CLARIFICATION_RULES注册表。它属于对话完整性决定，不应套进资金风险规则的observe开关。它触发时approved=false、violations为空，表示信息未齐而非用户违法或业务越权。

### 9.3 enforce 和 observe

enforce命中时进入violations，导致approved=false，通常不产生批准证书。observe命中时进入would_block，仍可approved=true，并记录would_block审计事件。observe适合新规则校准：先看它会影响哪些请求，再决定是否升级为强制阻止。

R4虽然是observe，但当前周期执行路由、Plan限制和长期订单模块共同决定周期转账不能直接变成自动扣款。因此系统的实际安全边界不只取决于R4的模式。反过来，也不能因为某次verify返回approved就认为所有业务约束都已经由该注册表检查完毕，额度、归属、令牌等还有专门代码。

### 9.4 检查发生在哪些位置

计划步骤准备前会调用verify并保存plan_prepare记录。底层prepare函数在关键边界调用boundary，准备好操作单后还可保存prepared_snapshot记录。confirm_proposal在确认事务内调用boundary，确保批准不是只发生在对话阶段。

某些规则在不同阶段不适用，例如没有proposal时R3没有快照可比；没有amount_minor或来源ID时，R2无法检查完整业务余额。因此规则通过列表要结合phase、action和params理解，不能把“不适用时无违规”解读为进行了全面资金证明。

### 9.5 证书的字段

通过时证书包含ruleset_version、rules_passed、clock_now、action_digest和rule_modes。action_digest是action与params的规范化JSON哈希，用来关联“这一份参数的这一次规则检查”，并非电子签名。VerificationRecord保存结果JSON，AuditEvent通过记录编号关联审计事件。

证书没有证书颁发机构，也没有私钥签名；SQLite数据本身还需要生产级权限、完整性保护和备份策略。它证明的是当前已编码规则对该结构化动作的检查结果，不证明法律合规，不证明用户自然语言必定被理解正确，也不证明所有未来时刻都可执行。

### 9.6 R1 的价值与边界

R1针对的是最危险的一类静默降级：“如果工资到账才转100元”被模型简化成“转100元”。项目使用统一条件词表，尽量让旧mock、新Plan和确认边界共享条件识别。

关键词检测仍可能漏掉没有显式条件词的复杂含义，也可能把普通叙述中的条件词当成业务条件。当前处理偏向保守澄清，但其准确率和误拦截率尚未经过真实语言大样本评测。报告不能把“R1存在”写成“任意中文条件都不会丢失”。

## 10 时间表达和统一时钟

### 10.1 为什么时间必须由后端计算

“本月”“昨天”“每月31号”都依赖当前时间和业务时区。若模型直接写绝对日期，就可能使用错误年份、旧上下文或自己的时间假设。统一Clock让查询范围、操作单有效期、会话过期和周期到期共享同一个时间来源。

模型仅翻译时间表达。例如本月是period=this_month，昨天是period=yesterday，每月15号是recurring monthly day=15。后端注入Clock时间，让模型理解语境，但最终日期仍由period_args和月度调度代码计算。

### 10.2 RealClock 和 ManualClock

RealClock返回当前UTC时间。ManualClock保存一个可推进的带时区时间，并用RLock保护读写。未注明时区的初始datetime按Asia/Shanghai解释，再转成UTC内部存储。business_day从Clock转换为上海日期。

手动Clock默认初始值兼容演示库demo_date。调试advance接口只在manual且本地演示请求下可用，days要求整数、0至366。推进时间后，会延长当前页面会话以便继续演示，但不会延长已有业务操作单有效期；这些操作单仍按新Clock过期。

### 10.3 查询范围

period_args将this_month解析为本月1号至当前业务日，将last_month解析为上月完整月份，将today和yesterday解析为单个本地日期。offset的day表示指定天偏移，month表示shifted_month得到的偏移日期；它不是自动理解成“前几个月合计”。

日期接口通常用包含首尾日的start与end，底层会转换为UTC半开区间，形如[start_utc, end_exclusive_utc)。半开区间能让相邻日期没有重复边界：当天零点包含，下一天零点不包含。

### 10.4 时钟和业务入账时间的关系

旧domain/clock.py保留业务日和业务时间的适配方法，新app/clock.py成为实际时间来源。账本保存posted_at_utc与created_at_utc两个字段，前者是业务入账时刻，后者是记录生成时刻。在演示中可以用业务日期构造可重复的入账范围，同时用Clock判断会话和操作单期限。

### 10.5 运行限制

ManualClock在进程内存中共享，不是数据库持久化时钟。重启会根据演示设置重新初始化；多API worker会各自持有不同时间。因此当前启动器固定workers=1，手动演示不适合多进程部署。

当前Plan未加入一般once date的未来转账表达。transfer的params.time被明确拒绝，并提示是否现在准备操作单；每周、每日等重复频率也不属于已实现的长期执行能力。Schema设计有结构化时间，不等于已经支持所有时间词语。

## 11 R10 周期字段完整性

### 11.1 这次修订解决的实际问题

此前用户只说“转账给林晓100元”，助手却反复询问单次还是每月。原因不能简单归为“LLM不好用”：提示词把周期选项、缺日期追问和默认建议写在了理解层，旧问题又进入对话历史，模型容易将它们当成需要继续确认的事项。

修订后，提示词只说明时间字段怎样翻译，未提及部分填null，不假设时间，不主动进行时间追问。后端规则拥有“是否追问”和“建议什么默认值”的决定权。为了进一步抵挡模型违反提示词，temporal.normalize会核对周期信息是否有真实用户依据。

### 11.2 用户依据的建立

temporal.resolve只扫描active_dialogue中的user消息。当前识别“每月”和“每个月”建立monthly依据；识别明确单次或否定周期的语句清除周期要求；对于每周、每天等标记，记录不支持的频率并走明确停止路径。

它为周期请求生成anchor，使用消息ordinal和内容的SHA256。anchor用来把“同意默认日期”绑定到当前周期要求，避免一条旧确认污染另一条请求。日期提取支持阿拉伯数字及一部分中文数词号日表达，要求1至31。

这个依据提取器本身也有词汇范围。诸如“以后每逢发薪日”不能仅凭推测变成monthly day=1；应继续澄清或扩展表达。更复杂的否定和转述也需要后续测试。

### 11.3 模型信息如何被纠正

normalize清除每步的recurrence，并依据用户时间状态为可适用的计划设置统一顶层周期。用户无monthly依据时，模型自行加入的周期会被删除。用户说每月但无日期时，模型填的15或1也被改回null。

每次纠正记录field、observed、resolved和reason。这样不必靠肉眼判断“模型是不是老往每月想”：Trace直接显示它曾生成什么，以及服务端接受什么。

### 11.4 何时提默认1号

R10的确定性条件是：动作是plan，有用户周期依据，recurrence.freq为monthly，recurrence.day为空。首次返回：

“每月转账需要固定日期，设置为每月1号可以吗？”

这句话中的1是规则建议值，不是直接写入最终长期指令的默认值。后端保存temporal_pending，包含规则编号、anchor、suggested_day和实际问题。此时没有StandingOrder，没有Proposal，也没有资金变化。

### 11.5 怎样接受默认值

后端要求当前待确认的anchor匹配，并且最近助手消息确实等于保存的后端问题，才允许“可以”“同意”“好”等受支持的明确回复采用1号。助手自己提出的泛泛每月建议没有temporal_pending，不能因为用户说“对”就凭空创建周期或日期。

接受后保存temporal_accepted，包括anchor、day、rule_id和user_reply。后续模型即便还输出null，时间依据也能保留后端确认的1号。不过具体长期指令仍需页面确认，聊天里的“可以”只确认日期建议，不授权扣款。

### 11.6 拒绝与补充

用户“不行”“不要1号”“不选1号”会标记当前anchor拒绝默认值，继续保留day=null。后端改问：

“请告诉我每月几号转账（1至31号）。”

日期提取避免将“不要1号”中的1误当成用户选择。之后补“15号”，可采用15。用户改为“不需要每月，只转一次”，会清除周期状态和相关历史确认。这里的确定性针对已经编码的语言匹配范围，不代表任意含蓄答复都能被正确理解。

### 11.7 三个验收输入

| 用户输入 | 周期依据 | 日期 | 后端行为 |
| --- | --- | --- | --- |
| 每月转300给张三 | monthly | null | 必触发R10默认日期确认 |
| 每月15号转300给张三 | monthly | 15 | 不触发R10，继续业务信息校验 |
| 转300给张三 | 无 | 无 | 不出现周期询问 |

第二、第三个输入不问周期，并不意味着一定能立即准备转账：缺少付款账户或张三同名仍要询问。验收把“日期是否齐全”和“业务槽位是否齐全”拆开，避免用一句笼统的“成功”掩盖真正的检查目标。

### 11.8 规则追问如何记录

R10写入VerificationRecord，phase为plan_clarification，clarifications记录规则、字段、观测值、期望值、问题和suggested_value。AuditEvent为clarification_requested，detail_code含R10和记录编号。Trace.verification.approved在有追问时为false，且violations仍为空。

这让“信息缺失”“业务违规”“接口错误”可以分别统计。以前机械的“两轮修复仍未通过”常把不同原因混成同一种回复，现在R10日期问题有独立证据，HTTP问题也有独立model_error。

## 12 单笔转账与确认事务

### 12.1 精确金额

后端以整数分保存金额和余额，Decimal处理元字符串，不接受浮点数作为资金参数。100.01元变为10001分，而不是依赖二进制浮点乘法得到近似值。validate_minor还排除bool、负数、零和超过64位范围的值。

演示额度为单笔500000分、单日累计1000000分。日累计从已入账的internal_transfer和external_transfer借方流水按上海业务日统计，不使用模型记忆或前端缓存作为额度依据。

### 12.2 prepare 阶段

prepare_transfer验证币种、金额、目标类型、备注长度和条件结构，生成规范化请求摘要。相同待处理请求可以复用现有操作单；与当前活跃写任务冲突的请求按既有任务机制处理，避免同一会话同时出现多张竞争的写申请。

有消费条件时，先实际统计；不满足则返回condition_met=false，不创建转账申请。接着校验来源账户、日累计、余额、目标归属与状态，记录资源版本快照，创建Proposal和底层Task。

### 12.3 操作单固定了什么

Proposal保存params_json、snapshot_json、params_digest、dataset_version、session_id、status、token_hash和有效期。摘要对参数、快照和数据版本一起计算，使用户看到的申请与确认时使用的内容建立一致性检查。

典型快照含来源账户version和余额，目标本人账户version或收款人version；卡操作含卡版本、卡状态、关联账户版本和状态。版本变化表示资源曾经改变，要求重新准备，而不是在确认时悄悄替用户重新选对象。

### 12.4 页面确认令牌

页面获取confirmation-token，后端随机生成token_urlsafe(32)，只保存令牌哈希。确认时用hmac.compare_digest比较。令牌与具体操作单关联，不能被模型工具获取，也不能用聊天“确认”替代。

操作单有效期是5分钟，由统一Clock判断。请求令牌不延长原操作单期限。长期指令的确认请求也使用独立的5分钟期限和哈希令牌，不能与单笔令牌互换。

### 12.5 确认事务的复核顺序

confirm_proposal先验证会话和操作单归属。如果已executed，直接返回原回执，避免重复扣款。未执行则检查待确认状态、有效期、令牌、参数摘要；消费条件在数据库当前状态下重新计算；验证器检查余额与快照；业务函数继续检查账户状态、额度与余额。

检查完成后才调用账本写入。资金和版本变更、TransferOrder、BusinessResult以及审计状态共同提交。若中途抛出异常，事务回滚；必要时另记失败审计，原业务不会留下半笔转账。

### 12.6 内部和外部转账

本人账户互转写借方和贷方两条流水，共享business_id。来源余额减少，目标余额增加，两个账户版本递增。对预置收款人的模拟外部转账只在本地账本写来源借方；项目没有真实外部银行贷方确认渠道。

Transaction对business_id、account_id、type有唯一约束；TransferOrder对proposal_id和business_id唯一；BusinessResult对proposal_id唯一。确认逻辑先检查已执行状态，数据库唯一约束再提供重复记录防线。这个组合支撑重复提交返回原回执的幂等行为。

### 12.7 参数修订和取消

用户在待确认时改变金额、对象或条件，旧申请需要失效并重新准备，不能直接改已固定参数后继续使用旧令牌。取消待确认任务会停止剩余步骤，并取消或失效未执行操作单。

取消任务不会撤销已执行交易。这是当前明确行为，项目未实现转账冲正或退款业务入口。不能在用户“取消整个计划”之后宣称前面已经确认的转账自动撤回。

### 12.8 SQLite事务边界

atomic_write在最外层使用BEGIN IMMEDIATE，并在进入前回滚旧读事务和清理ORM缓存；内层使用savepoint。commit helper在原子范围内只flush，避免嵌套模块提前提交外层事务。

SQLite提供本地写事务串行化，适合当前小型演示。它不具备跨数据库或跨服务原子性，也没有生产支付清算的失败补偿机制。数据库繁忙会返回RETRYABLE_CONFLICT，前端应先查原操作单状态，而不是一看到网络失败就新建另一笔转账。

### 12.9 账本一致性核对

ledger_errors可以对演示库做一致性检查。它验证流水账户与owner和币种匹配、交易卡归属一致、类型方向金额正确、退款确实引用原消费且不超额。对每个账户，还检查“期初余额加全部已入账贷方减全部已入账借方”等于当前余额。

对于本人账户互转，同business_id应有两条金额相同、方向分别为借贷、账户不同且owner一致的流水。这些不变量让余额和流水能够相互核对，不只依靠界面显示。该函数是内部诊断方法，不意味着每轮聊天都会自动全库核对，也不是对外的实时监管审计接口。

## 13 账单消费统计与证据

### 13.1 统计口径

消费统计只计已入账posted的purchase和refund。消费增加purchase_minor，退款增加refund_minor，net_minor等于消费减退款。income、internal_transfer和external_transfer不计入餐饮、购物等消费额。

例如餐饮消费1200元、餐饮退款200元，净消费是1000元。把“账户一共流出了多少”直接当作“消费多少”会把转账误计进来，当前账本类型能将这些概念分开。

### 13.2 退款与原消费

账本要求退款引用本人已入账的原消费，并且退款账户与原消费一致，累计退款不超过原金额。退款沿用原消费类别和卡片，不让模型或新退款随意改类别。

统计按退款自己的入账时间计入当期。因此本月退回上月购物款时，本月净额可能下降甚至为负。这不一定是错误，报告和页面需要同时展示消费与退款，而不能把负净额强行改成零。

### 13.3 数据覆盖完整性

DataCoverage保存每个账户的已知完整时间区间。统计查询会把查询范围与这些片段比较：只有每个所选账户的完整片段连续覆盖全部查询区间，is_complete才为true。

没有查到消费流水不等于“确实花了0元”。如果数据范围不完整，只能说当前已知数据中的金额。消费条件也要求complete=true才可判定成立，因此缺失记录不能被误当成低消费，从而触发错误转账。

### 13.4 汇总与分页分开

_summarize_period从全部匹配入账行计算总额和类别结果，然后只对evidence.items分页。默认证据页20项，允许1至100项，offset必须非负。改变明细页不会改变统计总额。

返回包含period、coverage、totals、categories和evidence，证据提供transaction_id、金额、带符号金额、类别、商户、入账时间和原消费引用。读者可以由汇总回溯到具体流水，而不是只能相信模型一句总结。

### 13.5 比较口径

旧统计服务支持previous_corresponding、previous_full_month、自定义范围和none。当前净额与基期净额都完整时才给差额；基期净额大于0才给百分比，使用Decimal并四舍五入到一位小数。数据不完整或基期非正会返回原因，而非伪造增长率。

新Plan的summarize_spending编译明确设comparison_mode=none。也就是说，底层服务和前端已有比较能力，新模型Plan暂未开放完整比较参数。如果用户要求“本月同比去年”，不能在新版Plan中偷偷退回普通本月合计。

### 13.6 条件消费与普通账单

普通账单查询展示统计和证据；条件转账将同一个统计结果用于后端布尔判断。threshold_minor是整数分，gt是严格大于，lt是严格小于。恰好等于500元时，“超过500元”不成立，不能将“大于”和“大于等于”混用。

确认阶段重新统计，防止操作单准备后增加退款或修正流水导致条件已经变化。这里的可验证性来自同一计算服务与固定条件，模型不自行决定“看起来超过了”。

## 14 卡片管理与跨场景流程

### 14.1 冻结和解冻

list_cards查询当前用户卡片。prepare_card_action只接受freeze和unfreeze，解析唯一卡片后生成固定申请。确认事务核对卡版本、卡状态及关联账户版本状态，再更新卡状态和version，写CardActionOrder与BusinessResult。

如果卡已经是目标状态，既有服务可返回already_in_state，而不制造重复状态变化。前端对此显示无需新建操作单。冻结影响后续模拟消费的可用性，但不改变既有消费流水，也不删除历史账单。

### 14.2 旧跨场景模板保留的价值

agent/crossflow.py保留受限场景模板，包括消费阈值后转账以及先调查交易再关联卡片操作等流程。旧条件类型中有transaction_card，它固定交易ID、卡ID、账户ID、尾号、金额和入账时间，确认时重新核对关联。

新版模型Plan的Condition只开放消费净额gt或lt，并未完整表达transaction_card类型。因此不能说新Plan已经覆盖旧模板每个细节。保留旧模板一方面维持已有功能，另一方面作为服务故障时的已知场景降级来源。

### 14.3 交易调查不等于异常检测模型

查询某段时间交易、让用户核对不认识的消费、准备冻结相关卡，是基于业务证据的调查流程。它不等同于训练了欺诈分类器，也没有经过异常检测召回率和误报率评测。比赛展示中可以讲“流水证据与卡片操作联动”，不宜声称已经识别所有异常交易。

## 15 周期指令和月度调度

### 15.1 长期指令与单笔操作的区别

StandingOrder保存以后每月准备哪一笔转账，包含固定业务参数与schedule。用户确认长期指令后，status变为active。到期时调度器调用普通prepare_transfer，生成每月对应的Proposal，用户还要确认该期操作单。

因此系统自动的是“发现到期并准备申请”，不是“持续授权后台直接扣款”。这是当前代码明确行为，也是与某些真实自动代扣产品的区别。长期确认摘要直接写“每次仍需页面确认”。

### 15.2 创建与锁定

prepare_order要求monthly且day为1至31，验证转账参数、来源归属、目标可用性、不同账户和金额。周期与消费条件组合在当前版本明确拒绝，要求分别提出。

长期指令哈希覆盖owner、dataset、action、params与schedule。最初状态pending_confirmation，再建立operation=activate的StandingConfirmation。确认时检查请求归属会话、期限、哈希和令牌，成功后记录activated_at并置active。

### 15.3 月末日期

monthly_due计算min(指定日, 当月天数)。每月31号在4月落30号，在平年2月落28号，在闰年2月落29号。它是在当月最后一天处理，不是推到下月1号。

这个政策写在代码注释、确认摘要和测试中。明确政策能避免用户和调度器对“31号不存在”产生不同理解。它是项目设计政策，不是自然语言模型自行补出的推测。

### 15.4 tick 怎样发现到期月份

tick扫描当前用户当前数据版本的active指令，从激活月份到今天的月份逐月计算到期日。早于激活日或晚于今天的期次跳过。每个期次用YYYY-MM标识period，先查已有StandingOccurrence，再处理尚未登记的月份。

数据库有(order_id, period)唯一约束，防止同一长期指令同月重复记录。已登记月份不会因重复tick再生成；已经执行的操作单也不能重新领取并扣款。

### 15.5 跨月推进和积压

如果手动日期从9月推进到11月，调度会发现中间已到期月份，而不是只检查“今天是不是扣款日”。但既有一活跃写任务限制会串行化操作单：某期先生成待确认申请，后续期次因ACTIVE_WRITE_TASK_EXISTS暂缓。

暂缓记录会删除尚未完成的occurrence，返回deferred通知，让后续tick在前一张操作单处理后重试。这样的积压处理可以避免同一会话突然出现多张竞争申请，但也不是无限吞吐的批量结算调度器。

### 15.6 余额不足和其他业务失败

prepare_transfer若报余额不足等DomainError，该月occurrence记skipped并保存中文消息与错误码。它不会静默重试到某个未来时刻自动扣款；重复tick看到该期已登记会跳过。用户能够在通知中看到未执行原因。

已有待确认操作单属于deferred，不等同于永久skipped。两类必须分开统计：一个是业务不能成立，一个是当前资源暂时被另一申请占用。

### 15.7 真时钟调度与离线会话

real模式下，若FINAGENT_SCHEDULER不是off，启动线程每30秒检查active指令所属用户。用户会话过期时，后端建立或延续专用standing_scheduler会话用于准备普通操作单。该会话用于调度，不代表模拟用户已经在页面确认。

线程是本地进程中的daemon，不是独立持久化任务系统。进程关闭后它停止；重启通过已有数据库记录发现未处理期次。当前没有分布式领导者选举、任务队列或跨实例租约机制。

### 15.8 到期操作单领取

当前页面会话可能与调度准备时的会话不同，原操作单也可能已经过期。claim_occurrence核对用户、订单状态和长期哈希；若已执行，直接返回已执行状态；若同会话且仍有效，返回原操作单。

否则，它使旧待确认操作单失效，再通过普通prepare_transfer为当前会话重新准备。它没有改写原固定参数和令牌，而是产生新申请并更新occurrence关联。于是跨会话查看长期通知仍然走正常页面确认。

### 15.9 暂停 恢复与取消

pause只接受active，resume只接受paused，二者通过受CSRF保护的请求直接改变状态并记审计。cancel先生成取消确认请求，页面确认后才把订单置cancelled，并使有关未执行操作单失效。

暂停控制未来tick，但当前代码暂停并不批量失效已经生成的操作单，也不能把“暂停”宣传成撤销所有未确认申请。取消已经确认的长期指令则处理仍待确认的期次申请；已执行的业务不会撤回。

### 15.10 管理聊天

用户说查询、暂停、恢复或取消定期转账时，standing.handle_chat可走管理路由。有多个长期指令时需要编号；只存在一条可管理指令时可以确定目标。聊天取消长期指令仍只是准备取消确认，不能直接绕过页面。

### 16.3 数据版本

dataset_version标识当前演示数据集。切换或重置数据后，旧会话、操作单和长期指令不应继续在新数据版本中生效。业务读取和长期订单owned都会核对版本，避免旧ID碰巧匹配新数据导致错误操作。

Trace与VerificationRecord当前按owner归属查询，但没有独立dataset_version列；同一owner历史记录的生命周期控制需要后续完善。它们不应被当成带完整数据版本隔离的永久合规档案。

### 16.4 存储与维护边界

默认SQLite路径为var/finagent.sqlite3，FINAGENT_DB_PATH可指定其他位置。连接启用foreign_keys=ON。当前没有为新增表设计独立迁移版本链、自动归档、容量上限或日志保留策略。

Trace默认开启会持续增长，也包含用户输入和计划语义信息。未来演示外使用应设置保留期限、访问权限、备份和敏感数据处理策略。当前HTTP诊断会清理密钥，但并不等于所有Trace文字都脱敏。

## 17 身份隔离和授权边界

### 17.1 身份来源

require_demo_session从Cookie读取会话，检查是否存在、是否过期、是否与当前数据版本一致。可选X-FinAgent-Expected-User用于识别其他标签页切换用户造成的身份变化。

这个系统没有真实银行身份认证、实名核验、设备认证或多因素认证。演示身份选择是方便验证数据隔离的机制，不应被描述成生产登录系统。

### 17.2 三种不同的令牌

会话Cookie定位当前演示身份；CSRF令牌证明写请求来自当前会话页面；确认令牌批准某一张已经固定的操作单或长期确认请求。三个令牌的作用不同，不能因为通过CSRF就认为用户批准扣款，也不能把模型的自然语言肯定当成确认令牌。

### 17.3 同源检查

require_write_protection优先用Origin，缺失时可解析Referer，要求它等于请求scheme与Host构成的来源，或明确配置的FINAGENT_ALLOWED_ORIGIN。之后比对X-FinAgent-CSRF与会话令牌。

先前页面“请从当前页面发起操作”源于开发代理改变Host，使浏览器Origin与后端判断的来源不一致。Vite代理changeOrigin=false修复这一开发链路问题，同时保留错误Origin与缺少CSRF的拒绝行为。

### 17.4 模型不能访问任意资源

模型Plan只用限定字段，compile_step从owner限定的数据集解析对象。get_task_status还要求Task属于同owner、同session、同dataset版本。Trace和验证记录查询按owner过滤，长期订单和期次管理也检查owner。

这些约束阻止模型通过猜ID读取别人的业务对象。但它们不能取代部署级授权审计、访问日志和真实身份体系；模型提示注入防护目前主要是提示约束、工具白名单、参数约束和服务端归属过滤的组合。

### 17.5 敏感信息与日志

模型请求包含用户需求、目录和对话，因此使用真实数据前必须明确第三方模型的数据处理边界。当前http_diagnostic只保留必要错误字段，并替换API密钥、Bearer值、完整输入和对话内容中的匹配敏感文本，避免直接保存整份请求响应。

这种诊断清理不构成通用隐私脱敏器：供应商错误中若只引用了姓名片段或其他未匹配的片段，仍可能留在message。Trace本身保留原始input，不能宣传成完全匿名日志。


## 18 Trace 与调试方法

### 18.1 Trace 记录什么

Trace是一次对话请求的可观察过程记录。它保存input、understanding、emotion_flag、plan、verification、temporal、model_error、repair_rounds、repair_history、outcome、clock_now和latency_ms。

其中understanding.intent来自任务状态，params优先取后端保存的槽位，emotion来自Plan或模板识别。因此它不是模型原始语义解析对象的完整逐字段副本。plan才是候选资产的主要展示位置，temporal则显示后端实际接受的周期依据。

### 18.2 关键字段怎样读

| 字段 | 重点看什么 | 容易误读的地方 |
| --- | --- | --- |
| plan.source | model、template或fallback | source=model不证明语义正确 |
| plan.steps | 工具、参数、依赖 | 候选步骤不等于都已经提交 |
| plan.recurrence | 被后端归一化后的周期 | 不代表原始模型一定如此输出 |
| verification.violations | 规则编号和hint | 空数组不等于所有业务都可执行 |
| verification.clarifications | R10等确定性问题 | 是缺信息，不是风控违规 |
| verification.records | 本轮新增检查的phase和证书 | 不同phase证明不同内容 |
| temporal.intent | 用户周期依据、日期、拒绝与接受状态 | 当前识别范围仍受词法规则限制 |
| temporal.corrections | 模型原字段与接受字段 | 可识别模型自行添加时间信息 |
| model_error | HTTP状态、供应商错误、请求编号 | 接口故障不应让用户补账户来修复 |
| repair_history | previous_plan和结构化违规 | HTTP400不应消耗计划修复轮次 |
| outcome | 请求结束时任务状态 | gathering_info有多个不同原因 |
| clock_now | 当时统一Clock | 手动模式可能不是现实今天 |

Trace的approved由该轮新增记录与违规、追问汇总，含义是这一轮记录中的检查结果，而不是永久执行许可证。真正的交易完成应看Proposal.status=executed和BusinessResult回执。

### 18.3 页面查看

展开“调试日历 定期转账与验证轨迹”，点击“查看本次验证轨迹”。该按钮依据最近trace_id调用GET /api/debug/trace/{id}。如果Trace开关off，就没有这轮新记录可查。

查看旧Trace需要有效演示会话且属于相同owner。直接在未登录浏览器打开接口可能得到SESSION_EXPIRED，不能因此认定Trace丢失。API响应还有统一envelope，实际Trace对象位于data字段。

### 18.4 判断机械回复的来源

当前回复有三类来源。非时间业务澄清可以来自模型的clarification；R10、接口故障说明和不支持能力说明来自后端；余额查询、操作单摘要和回执通常由固定模板根据真实工具结果生成。

所以“回复像规则文本”不能证明整个智能体没有使用LLM，也不能证明模型理解正确。应看plan.source、model_error、repair_history以及具体clarification。最终业务文案采用模板有助于忠实陈述数据，但普通对话流畅性仍有改进空间。

### 18.5 用户提供的 HTTP400 轨迹怎样解释

当时轨迹中steps为空、source=fallback、P_RESPONSE观测值为“计划模型返回HTTP400”、repair_rounds=2并出现P_REPAIR_LIMIT。它说明模型接口请求没被接受，系统根本没有得到正常Plan；不是林晓这个名字自然语言难理解导致的业务校验失败。

旧代码中DomainError继承ValueError，宽泛异常捕获把HTTP故障包装成PlanInvalid，造成无意义的定向修复和机械兜底。修复后DomainError先单独抛出，HTTP400在model_error中明确出现，repair_rounds为0。这修正的是错误分类和诊断能力，不等于供应商400从此绝不会出现。

### 18.6 一套实际排查顺序

第一步看model_error，先排除密钥、模型名、请求格式、配额和网络。第二步看repair_history，定位结构与语义错误。第三步看clarifications，分清确定性日期问题和普通槽位问题。第四步看steps、依赖和结果，确认计划覆盖了哪些任务。第五步看proposal与回执，判断业务是否真正执行。

最后核对clock_now和当前用户。错误日期、过期会话、未重新启动后端或继续旧任务，都可能使对话表现与当前配置不一致。先定位发生错误的层，再改变那一层的配置或规则，比不断加长提示词更有效。

### 18.7 耗时如何解释

latency_ms.parse包含生成、修复和有关解析过程，verify汇总执行器记录的规则检查耗时，total是traced_send整轮经过的总时间。它们不是严格互斥的三个阶段，也没有覆盖用户思考和点击确认的等待时间。

HTTP超时30秒，最多3次生成在最坏情况下可能显著拉长响应。工程测试使用替身，不代表真实模型请求的p50或p95。若后续研究延迟，应另外记录网络、生成、落地、数据库锁等待、prepare和confirm的独立计时。

### 18.8 Trace 的已知观察限制

当前fresh验证记录依据同owner请求前后的记录集合求差，不使用独立request_id严格关联每条验证记录。同一个用户并发请求时，其他请求的新记录可能影响汇总。这是后续适合增强的诊断关联点。

Trace在对话请求结束时保存，之后页面确认发生的验证记录不自动回写旧Trace；确认结果应查业务回执及对应验证审计。context中的诊断字段也可能来自最近一次成功计划，分析错误轮次时应联合model_error与实际记录，不能只相信一个可能保留的上下文摘要。

## 19 错误分流 修复与降级

### 19.1 四类失败不能混在一起

| 类别 | 例子 | 正确处理 |
| --- | --- | --- |
| 接口故障 | HTTP400、401、429、网络超时 | 诊断配置或受限降级 |
| 计划不合法 | 循环依赖、未知参数、丢条件 | 结构化反馈，最多两轮修复 |
| 信息不完整 | 缺付款账户、同名目标、缺每月日期 | 向用户提出必要问题 |
| 业务不能执行 | 余额不足、条件不成立、快照变化 | 拒绝、跳过或重新准备 |

统一说“请补充账户金额”会把接口问题推给用户；统一重新生成也会浪费调用；统一返回成功则会形成静默降级。当前修订让这几种路径有不同字段与错误码。

### 19.2 HTTP 状态的映射

| 供应商状态 | 当前错误码 | 主要排查方向 |
| --- | --- | --- |
| 400 | MODEL_BAD_REQUEST | Schema、参数、模型名、地址、网关兼容 |
| 401或403 | MODEL_AUTH_ERROR | 密钥及模型权限 |
| 402 | MODEL_QUOTA_ERROR | 账户余额或配额 |
| 429 | MODEL_RATE_LIMIT | 请求频率及供应商限制 |
| 其他非200 | MODEL_UNAVAILABLE | 服务可用性及网关错误 |
| 网络异常 | MODEL_UNAVAILABLE | 连通性、超时、代理 |

本地代理和模型供应商是两个不同网络段。页面出现CSRF_REJECTED通常是本地同源或会话问题，供应商400通常发生在后端向模型请求时。两者不能靠同一个“重新发送”操作解决。

### 19.3 HTTP400 怎么排查

先读取Trace.model_error的http_status、message、param、code、type和request_id。若param指向tools或parameters，重点看strict工具Schema；若指向model，核对配置模型是否支持该请求；若错误不含JSON详情，结合供应商request_id定位。

其次检查MODEL_BASE_URL是不是正确服务根路径，是否重复/v1或/chat/completions。检查thinking、strict和tool_choice是否被所用网关支持。当前wire Schema删除不支持的字符串数组长度限制，但后台完整约束仍保留。

最后可在独立测试环境构造最小请求，从一个只读计划开始，逐项增加Schema字段。不要在故障排查中打印完整API密钥或原始Authorization头，也不要以真实写业务作为模型连通性检查。报告中不含密钥，现有日志也不应成为密钥传播渠道。

### 19.4 定向修复的过程

generate循环每次先得到raw，再validate_asset，再调用semantic_check。捕获PlanInvalid后保存violations与previous_plan，作为下一轮反馈。成功返回plan、repair_round和history；第三次仍失败则附P_REPAIR_LIMIT，转向澄清。

定向修复比盲目“再试一次”更明确，因为模型知道哪个字段违反哪条规则。不过修复过程中仍可能改错其他字段，服务端每轮必须重新完整检查。当前未评测真实模型修复成功率，也没有证明一定收敛。

### 19.5 降级条件

MODEL_UNAVAILABLE时，代码可对detect完整识别的既有跨场景模板回退，并明确告知使用了旧模板。简单且不含条件、周期或多任务标记的单场景要求，也可用旧_resolve和registry执行准备或查询。

复杂要求无法可靠覆盖时停止，不把它偷偷改成单笔。HTTP400、认证错误、配额与限流没有被默认当作可用模板的理由；这保留了真正配置问题的可见性。回退也不能获得执行确认工具，仍需要固定操作单页面确认。

### 19.6 模型重复提时间怎么办

新版without_model_time_question识别模型时间问题。如果已有可执行步骤，则移除不必要时间澄清并继续后端检查；若空步骤只剩时间询问，使用受限模板重建业务槽位问题；涉及条件则保守要求完整条件说明。

这是防止模型违反翻译职责后继续绕进周期对话的后端措施。该函数仍依赖问题词表，且模板语义覆盖有限；它能通过已验收的场景，不等于消除所有语言歧义。

## 20 前端页面与状态同步

### 20.1 页面分工

AgentPanel承载聊天和任务步骤；OperationPanel展示固定业务摘要、确认和取消；SpendingPanel、SpendingChart及TransactionEvidence承载统计和证据；ConditionDetails展示条件及评估；NeuroPanel提供最简日历、长期管理、期次通知和Trace。

用户流中尽量展示账户名称、尾号、金额、条件和影响，而不是工具名称或内部字段。Trace区是开发调试入口，允许技术字段出现；它不能代替面向用户的清楚确认摘要。

### 20.2 为什么不能只相信前端状态

页面可能刷新、断网、失焦、多个标签页切换用户或在提交后丢失响应。服务端任务和回执持久化，是恢复状态的依据。useTaskSync在活跃任务时周期刷新，页面重新可见、网络恢复、窗口聚焦时也重查。

刷新请求带序列机制，避免旧查询响应覆盖正在进行的新操作。写请求期间暂停相关刷新竞争；错误时显示同步问题，要求从后端重新确认当前状态，而不把所有网络异常都当成业务未提交。

### 20.3 丢失确认响应

前端confirm失败后会先查询原任务。若proposal已executed，就显示原回执；如果仍待确认，才保留失败信息。这个行为配合后端幂等，避免“已经扣款但浏览器没收到响应”导致用户重复新建交易。

### 20.4 NeuroPanel 的当前交互

手动时钟页面显示模拟日期和推进一天按钮；长期指令可确认、暂停、恢复和准备取消；期次通知可领取本期操作单；最近Trace可展开为格式化JSON。

这是配套最简界面，不是完整日历产品。它目前没有复杂日期选择器、长期额度编辑器、图形化计划编辑器或专门的中文Trace时间轴。后台能力不能自动算作前端已经有完善交互。

## 23 与 VA NSF 思路的关系

### 23.1 从文献借鉴了什么

用户提供的VA NSF译文将类型化、模式锚定的AST作为神经理解与符号验证接口，强调类型检查、明确约束、批准证书、结构化违规和定向修复。FinAgent继承了这些系统分层原则，将Plan作为待验证中间资产。

本文的比较依据是所附中文译文和当前代码，不将译文中的实验指标当作本项目结果。特别是论文所述准确率、违规率和延迟属于论文的模型、数据集、规则集和环境，当前项目没有在同一基准上复现。

### 23.2 实现路线的区别

| 方面 | 所附文献思路 | 当前FinAgent实现 |
| --- | --- | --- |
| 语言模型 | 译文描述微调模型和定制生成 | 复用配置的DeepSeek兼容接口 |
| 结构生成 | FSM等语法约束解码 | strict工具Schema加本地类型校验 |
| 业务中间表示 | 领域支付AST | 类型化Plan与步骤依赖图 |
| 验证 | ASP和Clingo约束程序 | Python规则与业务事务检查 |
| 修复 | 结构化违规驱动 | 规则字段反馈，最多两轮 |
| 证书 | 规则相关正确性记录 | 规则版本、通过列表、动作哈希等审计数据 |
| 数据计算 | 文献平台主数据与执行环境 | SQLite模拟账本与数据覆盖 |
| 时间 | 文献方案中的交易语义 | 后端Clock和R10周期确认 |
| 执行授权 | 文献金融交易流程 | 固定操作单与逐笔页面确认 |

strict工具调用不是项目自行实现的tokenizer级FSM。Python规则也不是ASP求解器；项目没有Clingo、PDDL、LoRA训练或定理证明。工程采用更容易接入旧代码的路线，不能声称完整复现论文所有形式化保证。

### 23.3 当前方案增加的工程机制

对这个具体项目而言，新版增加了统一时间、月度长期指令、逐笔确认后恢复、用户语义依据、Trace、HTTP错误分流和R10对话政策。它将“问不问日期”变成可测试规则，并通过归一化处理防止模型擅自引入monthly。

这些是针对当前银行演示工作流的工程扩展，可以作为比赛技术贡献陈述。要证明其比论文方案“更好”，需要先定义比较目标，例如日期误问率、任务保留率或人机协作完成率，再做可比实验，不能仅凭模块更多得出性能更优。

### 23.4 可以严谨主张的价值

项目将不确定的语言草稿和确定的业务执行分开；把模型输出落到归属明确、金额精确、时间统一的业务参数；让规则拒绝、信息追问和接口故障各自有记录；在既有账本基础上保留页面授权和幂等回执。

这些价值可以通过代码和工程测试展示。模型鲁棒性、用户体验、修复收益与规则扩展成本则需要实验；法律合规和真实资金安全还需要正式业务、安全和部署体系。

## 24 当前局限与后续演进

### 24.1 语言与计划表达边界

当前支持有限工具、有限类别和有限条件。复杂金额计算、任意陌生收款人、周度周期、未来一次性转账、条件与周期组合、嵌套分支都未完整实现。极值请求目前追问统计对象，不能当作已经具备最大最小交易分析能力。

grounding使用词表和正则，对新表达可能漏检或误判。模型生成合法计划仍可能漏掉当前覆盖检测没有识别的任务。未来可考虑更明确的意图结构、逐槽位原文证据、否定作用域、业务相关读依赖检查，以及覆盖语义的专门验证器。

### 24.2 对话体验

系统业务回执大量使用模板，适合准确陈述状态，但语言可能机械。可以在“事实与决定已经确定”之后增加受限的表达层，把固定结构转换成自然、短而清晰的文案，同时禁止改变金额、对象、状态、授权和拒绝原因。

这类表达层不应重新决定是否追问或是否批准。R10已经说明，当决定归规则、表达归文案后，既能保持确定性，也能逐步改善聊天体验。当前并未加入独立LLM润色层。

### 24.3 验证证书与覆盖范围

证书是机器可读检查记录，没有签名或外部验证服务。某条规则不适用时也可能出现在通过列表。需要增加适用性说明、严格request关联、证书绑定的资源快照和验证接口，才能更清楚地支持审计解释。

所有业务约束并未完全迁入RULES注册表。额度、目标状态、币种和授权仍在业务代码中。这并非当前功能错误，但技术说明应诚实：现阶段是统一验证入口与既有业务防线共同工作，后续可以逐步统一政策管理。

### 24.4 部署与调度

SQLite和进程内Clock适合本地小规模演示。后台线程缺少生产级持久化任务队列、多实例协调、重试政策和监控。大量历史月份扫描和Trace全量记录差集在数据增长后需要优化。

将来若换PostgreSQL和任务队列，应重新设计事务锁、幂等键、领导者租约、期次状态和补偿，不能只把数据库连接字符串替换就宣称分布式安全。

### 24.5 安全与合规

当前缺少真实身份认证、银行授权、MFA、KYC、AML、正式审计签名、数据脱敏治理和外部清算回执。这些属于产品上线前的必需体系，但不是本次模拟比赛原型已经实现的功能。

后续安全工作应围绕实际部署和数据风险展开，先明确谁能访问、保留什么信息、第三方模型接收什么，再选择控制措施。本报告不把通用风险清单伪装成代码现有能力。

### 24.6 建议的演进顺序

优先完善真实模型最小请求兼容性、语言失败样本和日期误问率；再增强槽位证据、同名对象与任务覆盖；随后改善Trace的请求关联和中文展示；最后扩展表达类型与调度。先把现有三类场景跑稳，比同时添加大量不能验证的金融功能更可控。

## 25 实验方案与比赛展示建议

### 25.1 本章是建议 不代表已经执行

原用户要求先编程、暂不实验。当前只完成工程验证，没有真实模型效果对照。本章给出可直接执行的实验计划，实施时应使用独立测试数据、冻结版本和明确标注，避免影响正在演示的主库。

### 25.2 研究问题

第一个问题是结构化计划是否提高多任务与条件保留。第二个问题是规则反馈是否比泛泛重试更有效。第三个问题是R10是否降低无依据周期追问，同时保留必要日期确认。第四个问题是新增安全机制是否过度增加追问、拒绝和延迟。

每个问题都应同时测“正确接受”和“正确拒绝”。只证明危险输入被拒绝不够，因为把所有业务都拒绝也能获得很低违规率，却不能服务用户。

### 25.3 实验组和消融组

| 组别 | 改变项 | 主要用途 |
| --- | --- | --- |
| A 旧mock模板 | 无真实模型 | 工程回归和固定表达基线 |
| B 旧live路径 | 旧工具选择 | 对照现有语言理解链路 |
| C 新Plan主系统 | 当前全部机制 | 主结果 |
| D 去掉定向反馈 | 同样预算，泛化重试 | 测反馈信息的贡献 |
| E 去掉语义依据检查 | 隔离环境禁止真实写提交 | 测金额对象时间纠正贡献 |
| F 提示词周期政策 | 保持模型和输入一致 | 比较R10与模型决定追问 |
| G 关闭R10 | 独立影子评估 | 看缺日期的处理差异 |

危险消融组只能记录候选计划和模拟结果，不应在真实资金环境移除授权或余额检查。模型、温度与生成预算应尽可能一致，避免把模型换代收益算成规则收益。

### 25.4 数据集分层

建议分为六类。简单类含查询、完整转账和卡动作；缺信息类含缺来源、缺金额、同名与找不到目标；组合类含读后写、两笔写、顺序修改；条件类含大于小于、等值、否定、不能表达分支；时间类含本月上月、每月缺日、有日、拒绝默认、改单次；对抗类含助手建议污染、金额阈值混淆、目录注入、跨用户ID和旧任务授权继承。

可先建立约180个独立语义场景，每类约30个，再为每场景写2至4种自然说法。训练或调提示词使用开发集，最终测试集保持冻结；按语义场景划分，不能把同一个需求的近义句分散到开发和测试里造成泄漏。数量是设计建议，不是已完成数据集。

### 25.5 标注内容

每个案例应有用户输入、上下文、资源目录、Clock、期望动作序列、条件、金额、目标、时间、应该问的槽位、禁止问的槽位和允许结果。多轮案例还要标注每一轮用户修订的作用范围。

业务结果的真值最好是结构化对象，而不只是参考回复文本。对于“转300给张三”，若缺来源和同名信息，正确答案可能是一组等价的必要问题，而不是唯一一句固定文案。

### 25.6 主要指标

任务语义准确率按完整结构匹配评估，金额、对象、条件、时间和任务覆盖均正确才计全对。再分别给槽位准确率和多任务覆盖率，帮助定位失败层。业务完成率依据Proposal及回执，不能只看聊天声称成功。

违规率统计被系统接受但违反已编码或人工标注业务约束的请求。误拒率统计本可安全完成却被拒绝的请求。静默降级率统计语义丢失却仍声称完成且未明确说明的案例。不要把安全澄清排除后又宣称“100%用户完成”。

日期无关追问率定义为：没有周期要求的案例中，出现周期询问的案例数除以该类案例数。必要日期追问召回率定义为：明确monthly但缺day的案例中，正确触发日期问题的比例。日期齐全误问率记录monthly day已明确却仍问日期的比例。

修复成功率记录初次失败案例在预算内变成正确计划的比例；另外按0、1、2轮分布报告，不用平均轮数掩盖大量预算耗尽。报告每请求模型调用数、token成本、p50、p95、最大延迟、parse与verify耗时及数据库冲突。

### 25.7 多轮一致性实验

重点覆盖“每月转300—不同意1号—15号”“每月—只转一次”“先说100后改200”“先说张三再明确尾号”“已完成一笔后再来一笔但未给金额”。每轮同时查看上下文、计划和实际业务状态。

重复同一输入3至5次可观察模型波动，固定后端规则应保持同样的决策条件。不能为了追求一致而把模型计划内容写死成参考答案；要让模型真实生成，并保留raw候选与服务端纠正前后对比。

### 25.8 工程耐久实验

可在独立库测重复confirm、确认响应丢失、两个标签页竞争、模型慢响应后用户取消、跨月推进、session过期领取、余额变化、退款改变条件、短月31号和多长期指令竞争。

压力测试需与模型效果测试分离。模型接口限流、SQLite锁等待和前端同步不是同一种延迟。先在伪模型下测系统容量，再加入真实模型，才能分清瓶颈来源。

### 25.9 统计报告

使用同一案例成对比较系统组别，报告样本数、失败数和置信区间。将安全拒绝、必要澄清、模型接口错误和不支持能力分别列出；记录重试政策和供应商版本。保留失败样本，不能删除难案例后只展示最顺畅输入。

如果没有复现论文的数据和环境，应报告“本地银行演示数据上的对照”，不直接与论文准确率排列成同一个榜单。项目贡献可以通过特定任务的改善证明，而不必宣称所有指标都更优。

### 25.10 比赛展示顺序

建议先演示一笔查询后转账，展示Plan和页面确认；再演示消费条件不满足时不转账及证据；第三演示卡片冻结解冻；随后演示每月缺日期由R10追问、15号不再问、推进日期生成期次操作单；最后打开Trace解释为什么允许或停止。

现场不要把故障演示依赖真实模型随机出错，可以用已经保存的工程Trace和隔离重放说明错误分流。真实模型演示则应保留网络故障预案和mock备用，并明确说明切换。展示结论应聚焦“理解可灵活、决定有规则、执行要确认、过程可追溯”。

### B9 关键校验编号索引

| 编号 | 层 | 含义 |
| --- | --- | --- |
| P_RESPONSE | 模型响应 | 工具调用或JSON响应异常 |
| P_SCHEMA | 本地类型 | 类型、字段或空资产不合法 |
| P_DAG | 依赖图 | 重复ID、循环或未知依赖 |

| P_TOOL_PARAMS | 工具能力 | 该工具收到无法使用的参数 |
| P_AMOUNT_BINDING | 语义 | 转账金额与用户子句不符 |
| P_GROUNDING | 语义 | 对象金额日期缺用户依据 |
| P_TASK_COVERAGE | 语义 | 某些已识别任务被遗漏 |

### B10 最简核心算法

以下伪代码描述现有模块关系，不是可直接替换源码的实现。

```python
save_user_message()
payload = build_current_request_context()
time_state = resolve_user_time_evidence(payload)
plan = generate_and_validate(max_repairs=2)
normalize_model_recurrence(plan, time_state)

if R10_requires_date(plan, time_state):
    persist_rule_question()
    return gathering_info

if plan.clarification:
    return ask_business_slots()

steps = compile_all_semantic_parameters(plan)
persist_plan_version_and_steps(steps)

for step in topological_order(steps):
    if dependency_failed(step):
        mark_skipped(step)
        continue
    verify_and_record(step)
    result = execute_read_or_prepare(step)
    if needs_page_confirmation(result):
        return awaiting_confirmation
```

可写“我们实现了基于类型化Plan的神经符号银行代理，在准备和确认两个边界验证业务，并将周期日期完整性从提示词迁入确定性规则”。可写“193项隔离工程检查全部通过，真实模型效果评估尚未实施”。

不应写“形式化证明所有自然语言转账安全”“系统已超越VA NSF准确率”“模型不会产生任何幻觉”“每月自动扣款已实现”“已满足银行监管要求”。这些结论均超出现有代码和证据。

完整技术叙述应区分语义正确性、规则满足、授权正确性、事务原子性、用户体验和运维可用性。把每个层次的目标、实现和证据分别讲清，才能让评审理解项目真正完成了什么，也能让后续实验有明确的问题和评价标准。

### E2 当前设计应维护的不变量

金额最终以整数分进入业务函数；模型不能给自己添加执行或确认权限；对象解析限定当前owner；同一操作单参数一旦固定，修改需求要重新准备；确认时仍重查条件、快照、额度和余额；多笔写逐笔获得页面确认；每个长期指令每月只有一个期次记录；用户没提周期时不能被助手建议变成周期要求。

这些不变量由不同模块共同维护。后续加功能时，应先问新工具是否破坏其中某条，再设计Plan字段、规则、授权摘要和测试。不能只增加一个模型工具名就跳过完整业务流程。

### E3 一次技术评审可以逐项核对什么

看用户原文与当前未完成请求是否一致；看Plan是否保留所有写任务与条件；看工具能力之外的参数是否被拒绝；看对象和金额是否有依据；看R10是否只在有用户周期依据且缺日期时触发；看操作单是否固定；看确认事务失败后是否有半笔账本；看重复确认是否返回原回执；看Trace是否清楚区分模型、规则、模板与业务结果。

这一组问题比只问“能不能聊天”更接近当前项目的技术重点，也能把报告中的抽象架构转成实际代码审查和实验验收标准。
