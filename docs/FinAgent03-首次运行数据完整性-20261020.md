日期：2026-10-20。本轮从 GitHub main `80ff0412c57af1343cbc093d0535169eae478575` 下载干净源码，在隔离副本修复和验收；不重置作者运行库。

## 原因与完整性核对

GitHub 已包含完整 `datasets/demo_financial_v2`。将下载副本的 380 个业务源码、脚本及数据文件与本地 FinAgent-03 对照，内容一致（比较文本时仅规范换行），没有发现未上传的业务源码或年度 CSV。

实际缺陷是 `scripts/container-start.py` 在运行库不存在时仍调用旧 `app.data.cli reset`，产生三个用户；两个后端镜像又没有复制年度 CSV。以前的镜像健康、迁移和卷保留检查通过，不能证明年度数据正确装入。本轮补齐实际数据与 API 断言，不沿用旧健康结果证明数据完整。

## 实际修改

- `scripts/initialize-demo.py`：复用现有年度导入器，在隔离暂存库迁移、验证 CSV 摘要、核对账本及逐 CSV 归档行数，验证通过才原子发布首次运行库。没有数据时明确报错，不回退三用户。并发锁、发布时目标已存在拒绝覆盖、失败留存隔离诊断。
- `scripts/dev.ps1`：新安装缺库时自动调用年度初始化器；已有库继续增量迁移，配置错误不切换 Mock。
- `scripts/container-start.py`、两个 Dockerfile：空卷从完整年度 CSV 初始化；已有卷仍只迁移；镜像包含年度 CSV、初始化器和显式备份导入器。
- CI：cloud 镜像首次启动及重启均核对年度库；通过实际 `/api/demo/users` 核对 20 位用户。另构建并启动 Dockerfile.backend，验证它也装入同一完整年度库。
- README：明确首次启动的数量、三用户旧库的保留原因、显式备份替换与另开新克隆目录两种办法。
- CLI 的缺库提示及源码打包所需文件同步修订。旧三人种子保留给现有安全测试和显式重置，不再用于正常容器首次启动。

## 已有三用户库与恢复

更新源码不会替换已存在的数据库，即使它只有三位用户。最安全的体验办法是在另一目录全新克隆并启动，保留旧库。需要将旧演示库切换为年度数据时，先停止这个项目的前后端，再显式运行 `scripts/import-financial-demo.ps1`（Windows）或 `python scripts/install-financial-demo.py`（有挂载原卷的停止服务维护环境）。导入器先在线备份到 `var/backups/before-financial-install-*/finagent.sqlite3`，再校验暂存库并替换。

这是替换演示数据，不是将旧交易合并进新年度库；旧任务与业务记录仍在备份中。不要删除卷、运行 reset 或对运行库直接覆盖。失败时保留原库、暂存诊断及备份，先检查日志和磁盘；旧代码与备份的 schema 必须匹配后才恢复。
