# M2 验收记录

- 日期：2026-09-24
- 阶段：确定性金额、时钟、账本、退款、消费统计与可展开证据。
- 环境：Windows PowerShell 7.6.5；本机 Python 3.12.10；Node v24.14.0；npm 11.9.0；本地 SQLite。
- 种子：`m1-2026-09-24-1`，演示日期 2026-09-24；统计口径版本 `spending-v1`；当前应用模式 `mock`。

## 实现范围

1. `backend/app/domain/money.py`：整数分与精确十进制转换，拒绝布尔值、浮点、超过两位小数和 64 位范围外金额；固定 CNY、单笔 500000 分、每日 1000000 分的演示限额。
2. `backend/app/domain/clock.py`：独立 `demo_date` 与可注入 `system_now`；上海时区日期边界转 UTC；本月、上月同期、上月整月、昨晚和自定义区间。查询语义为左闭右开，API `start`/`end` 日期按含首尾天解释。
3. `backend/app/domain/ledger.py`：仅后端内部可调用的记账方法；账户/卡/收款人归属与状态、退款原消费及累计上限、日转出查询、本人转账成对记账、余额和卡关联核对。待入账、撤销流水不改余额。M2 未公开业务写入 API，也未实现确认；M3 将为这些方法建立确认和事务边界。
4. `backend/app/domain/spending.py` 与 `GET /api/spending`：只统计已入账消费减已入账退款，按退款入账期和原类别处理；聚合完整匹配集合后分页返回证据。完整覆盖零交易为零；覆盖缺口标记 `incomplete`，仅提供已知小计，不计算比较差额或百分比。
5. `frontend/src/SpendingPanel.tsx`：日期、账户、类别与比较模式查询；展示金额、消费/退款笔数、比较、覆盖提示和证据翻页。全程读取后端结果。

## 2026-09-25｜同伴评审问题回归

评审指出 5 处 M0–M2 实际问题；本次仅修复已完成阶段，M3 尚未开始。

1. 切换演示用户时立即使旧会话批次失效；初始化恢复、账户/卡/流水响应和错误都须核对批次。Edge 中受控延迟旧用户账户响应，切至新用户并释放旧响应后，页面保持新用户的账户与余额。
2. 消费证据分页沿用已成功提交的查询条件。Edge 中查询全部类别、把表单改成餐饮但不提交后翻页，第二页仍显示全部类别的证据与正确页数；提交餐饮查询后回到第一页。
3. 演示日期早于固定样例业务日时，不生成之后的已入账流水；退款引用与本人转账配对同步保留或省略。种子版本更新为 `m1-2026-09-24-2`，余额根据实际入账流水反推期初余额。9 月 10 日测试及实际重置验证未来已入账记录不存在且账本平衡；之后已恢复 9 月 24 日演示数据。
4. 流水类别“未分类”映射为数据库 NULL；所有无类别流水都可筛出，统计仍只计算消费和退款。测试核对 32 元消费同时出现在流水和消费证据中。
5. 安装脚本运行检测现有虚拟环境解释器；失效时自动重建，`-Python` 和 `-Rebuild` 可显式重建。已用本机 Python 3.12 执行 `setup.ps1 -Python`，重建、锁定依赖与前端安装均成功。

复验：后端 15 项测试通过；TypeScript/Vite 构建通过；Edge 浏览器流程通过。仍有一条上游 Starlette/httpx 弃用警告。原 M1/M2 验收记录保留作为当时结果，本节记录后续修正。
