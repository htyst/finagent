# G01 第一阶段：目标与节点契约

更新：2026-10-18。适用动态工具循环 `g01-v1`。本轮只交付串行目标台账与执行图，跨轮检查点、局部重规划属于 G01 第二阶段。

## 状态的唯一来源与兼容

目标、节点、队列和证据保存在原 `AgentTask.context_json.dynamic_runtime`，没有另建任务表或平行授权系统。任务 API 新增可选 `execution_graph`；`analysis_workflow` 保留供旧前端/旧任务使用。历史运行记录没有新 Schema 时，返回旧记录，不补造历史目标或依赖。

兼容的顶层 task.status 仍保留原接口语义，新的目标是否完成以 execution_graph.goals 为准，不能把一轮回答结束等同于全部目标完成。其他页面状态表达的统一属于后续 O01/T01。

新普通消息开始一个运行 ID，默认只有一个隐式目标。问候可以直接回答，不需要工具节点或复杂计划。多目标通过模型 `declare_goals` 明确用户原话，后续调用用可选 `execution.goal_ids` 关联；共享读取可以支持多个目标。模型可以先查询再明确目标，原节点与证据保留，已验证回答的事实引用建立支持关系，不改变旧调用依赖。

同批允许一个位于首位的目标声明和后续独立调用：先预校验目标、参数与引用，再按原循环逐项执行。整批不合法则不执行其中业务工具。后一个调用需要前一个尚未返回的事实时，仍须等待观察结果后再发起；没有增加并行执行。

当前运行台账跟随原 context 持久化。下一条普通消息仍按已有机制创建新的运行，**尚未实现跨普通消息的目标台账局部重规划**；已发生的业务写入、固定单、领域回执和历史对话保留。不能据此宣称 G01 第二阶段已完成。

## 公开数据契约

机器 Schema 由实际 Pydantic 类型导出，见 `本地历史证据：g01-phase1-contract.json（未公开）`。代码为 `backend/app/agent/execution_graph.py`，前端类型为 `frontend/src/executionGraph.ts`。

| 对象 | 字段 | 作用 |
| --- | --- | --- |
| graph | schema_version、task_id、runtime_id、plan_version、status、serial | 当前运行及服务端计划版本，固定串行 |
| goal | id、text、quote、kind、status | 用户目标与原话；kind 为 answer/query/analysis/operation |
| goal | evidence_refs、receipt_refs、needs_input、next_step | 有依据的进度、待补条件与继续方式 |
| node | id、task_id、plan_version、result_plan_version、name、title | 接受调用时的版本与固定单准备后的版本 |
| node | goal_ids、arguments、depends_on、dependency_sources | 目标关联、经过原工具 Schema 校验的参数和依赖出处 |
| node | observed_refs | 当时已可见的证据，不等同于数据依赖 |
| node | result_refs、receipt_refs、resource_ref、domain_status | 真实工具结果、领域资源及回执引用 |
| node | status、attempts、error_code、next_step | 执行、等待、失败和恢复提示 |
| node | policy、evaluated_risk、authorization_expires_at | 注册表风险属性、领域实际分级和授权期限 |
| node | reused_from、recovered_by、recovery_reason | 读取复用、已验证计算修正的真实引用；原失败不改成成功 |

内部节点另绑定 owner_id、session_id、dataset_version，保存与查询时核验归属。公开参数经已有隐私过滤器脱敏，完整收款账号、认证秘密等不进入图或外发模型上下文。前端仅展示目标、状态、缺项、调用与依赖，不展示模型私有思维链。

## 目标状态判定

| 状态 | 必须满足的依据 |
| --- | --- |
| completed | 普通问答已完成回答；查询已取得成功证据；分析已回答且没有待补条件；涉及业务写入时须有实际领域回执 |
| waiting_input | 工具等待补充业务字段，或有效回答明确 needs_input，或有效结构化财务回答存在必要 questions |
| waiting_authorization | 原工具停在固定单授权或受保护订阅查询范围确认 |
| failed | 未恢复的相关业务/读取节点失败，不能用随后一句回答抹掉失败 |
| cancelled | 可取消的未执行目标/业务已取消；已完成写入仍按真实回执显示 |
| pending / running / paused | 尚待处理、正在执行、被任务控制暂停 |

多个目标分别计算状态。有已完成目标且仍有未完成项时，图状态为 partially_completed。共享回答对旅行预算的追问不会把已经取得证据的余额查询一起标成未完成。固定单已准备不等于业务执行；预约、提交申请等领域状态仍显示原单真实状态，不把它们称为已经付款或获批。

## 依赖、引用与版本校验

1. `calculate.inputs[].node`、回答中的 facts.id / source_ref 等真实引用生成数据依赖；模型明确声明的前置调用单独标记来源并由后端检查是否成功。
2. 删除旧实现“前六个节点统一作为依赖”的规则。执行先后和上下文可见性通过节点顺序、observed_refs 表达，独立查询没有虚构依赖。
3. 依赖只能引用已有调用；执行图检查无环、节点/目标存在、字段类型与长度、参数不变和合法状态转换。前置失败的业务工具不执行。
4. 结果引用必须来自本次已保存工具证据；回执引用必须有匹配业务结果。结构化 synthesis 继续按原协议仅从已校验 fact_ids 生成来源，冗余的模型 evidence_refs 不成为图或回答依据。`evidence_refs` 只能填工具 source_ref，不能用 f1 等事实 ID 代替。
5. 保存时保留已执行节点，禁止改写其任务、用户、会话、数据版本、调用参数和策略。终态节点不能重新变成 running。补资料节点允许经可信表单转为待授权或读取完成。
6. 接受模型响应时继续核对请求控制、运行 ID、更新时间，并增加计划版本检查。过期响应不能覆盖新运行或暂停状态。
7. 固定单准备可能合法增加服务端 plan_version；节点保留接受版本，并另记 result_plan_version，避免把正常准备过程当成迟到结果。
8. 回执读取来自现有领域记录。即使授权提交后模型未回复，前端读取任务仍能取得真实回执；图投影只读，不重新执行付款。

计算修复仅适用于同目标、同一真实数据来源且全部用户明确常量保留的合法成功计算；原拒绝节点和错误码保留，前端显示“参数已修正”。读取失败、其他目标失败及删掉用户预算的计算不会因这项机制被掩盖。

## 权限与职责

模型只可提出目标、工具调用、字段和依赖，不能给目标填写完成状态或给节点自报风险。`registry.execution_policy` 从真实读取白名单、工具别名/固定动作及服务端红色动作集合导出元数据，所有节点 `can_submit=false`。

最终权限、跨账户日累计、订阅授权、模拟 MFA、幂等和业务写入仍由原领域服务决定。转账 metadata 的 dynamic 表示提交时按服务端规则重新计算，不代表绿色。小额申购、挂失、解挂等固定红色操作继续红色。查询授权不扩大成取消授权。

新增 `declare_goals` 仅记录元数据，不提交业务。没有新增执行 SQL、任意账户修改、授权签发、验证码输入或模型确认工具。模拟短信仍为本地模拟，不代表真实银行 MFA。
