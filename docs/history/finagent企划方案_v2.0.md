# FinAgent 企划与开发执行方案 v2.0

> 项目：面向个人日常资金管理与突发用卡问题的可执行银行智能助手。  
> 版本日期：2026-09-24。状态：内部产品与工程基线；可据此开展分阶段开发。  
> 版本关系：保留《finagent企划方案.md》作为 v1.0 历史版本。本文完整替代第一版的开发规格；发生冲突时，以本文为准。  
> 参赛背景：拟参加深圳国际金融科技创新大赛人工智能赛道。赛事信息沿用第一版提供的背景，本文未核验当届官方规则、资格、截止时间或指定技术要求，不构成已满足参赛条件的声明。  
> 本文规定的是待实现行为与验收要求，不代表相关功能、测试成绩或演示已经完成。

## 0. 给 Codex 的总执行指令

### 0.1 工作目标

按本文第 15 节的 M0—M7 顺序，逐步交付可启动、可验证、可演示的 FinAgent。优先完成模拟银行业务和确认执行链路，再集成自然语言 Agent，最后打磨评估与参赛呈现。

本文件是持续开发规格。用户只要求阅读、评审或修改方案时，不自动启动开发；用户要求“按第二版开始开发”时，从第一个未完成阶段开始落实。

### 0.2 必须遵循的工作方式

1. 开始前读取适用的 `AGENTS.md`、本文、已有代码和开发进度记录；检查工作区现状，不覆盖用户已有改动。
2. 先复用已有实现。阶段门槛通过后记录证据，再进入下一阶段；在用户已授权的开发范围内，不为普通可逆实现反复索要批准。
3. 不跳过记账、确认和权限验证，直接制作只会展示成功文案的演示页面。
4. 不把业务约束只写在提示词里。金额计算、资源归属、确认有效性、幂等和状态转换均由后端实施。
5. LLM 不可用时，业务 API、表单操作、固定演示和业务测试仍可运行；必须明确标识当前为 `mock` 模式。
6. 每阶段更新开发状态、实际运行命令、验收证据、设计决策及已知问题。没有运行的检查标记“未运行”，不得写成通过。
7. 遇到问题先定位并修复；外部依赖受阻时，继续完成不依赖它的工作，并明确受阻范围。不得把未通过的阶段静默标为完成。
8. 不自行接入真实账户或支付，不导入真实个人信息，不发布网站、不推送远端、不购买服务，除非用户另行授权。
9. 默认在当前任务中实施；不擅自引入多 Agent 开发或产品多 Agent 架构。
10. 阶段验收后进行一次范围复核。未经需求变更，不额外加入 RAG、向量数据库、长记忆、投资交易或复杂部署体系。

## 1. 产品定位、用户价值与参赛主张

### 1.1 一句话定位

用户用自然语言提出银行服务目标，FinAgent 根据账户与交易证据进行澄清和规划，在用户确认具体操作后执行模拟业务，并提供可核验的结果。

### 1.2 目标用户与问题

本版聚焦拥有多个日常账户、需要理解开支或处理用卡问题的个人用户。使用合成画像验证场景，不宣称已经完成真实用户调研。

| 用户问题 | 用户希望得到的结果 | FinAgent 的交付 |
| --- | --- | --- |
| 不知道本月餐饮开支为何增加 | 数字可信，能看到组成数字的流水 | 后端统计、比较区间、消费与退款明细及证据 |
| 希望快速转账但联系人同名 | 对象明确、金额正确、只转一次 | 澄清收款人、固定操作单、确认、交易回执 |
| 发现不认识的消费 | 找到对应交易与卡片，快速决定如何处理 | 证据查询、目标澄清、模拟临时冻结及结果 |
| 想按照消费情况调整账户资金 | 系统检查条件并按原意执行 | 结构化条件、执行前复核、本人账户间转账 |

### 1.3 核心价值假设

1. 对多步骤任务，自然语言可以减少页面切换与重复输入。
2. 当信息不完整或业务条件变化时，Agent 可以主动澄清，并给出清楚的下一步。
3. 结构化操作单、交易证据和任务轨迹可以帮助用户理解执行结果。

以上是待验证假设。通过第 13 节的对照试验给出证据，不能提前写成已证实结论。

### 1.4 差异化表达

参赛展示聚焦三个可验证能力：跨工具处理同一个用户目标；用业务数据而非模型猜测支撑数字和状态；在确认、条件变化和中断后仍保持执行结果一致。

不把“支持聊天”“用了大模型”或“接入多个工具”单独作为创新证明，也不在没有对照证据时声称优于现有银行产品。

## 2. 产品范围与优先级

### 2.1 必须交付 P0

- 三类单场景：账单分析、智能转账、卡片状态查询与模拟冻结/解冻。
- 两条跨场景流程：陌生消费与卡片处理；消费条件与本人账户间转账。
- 对话、账户/卡片面板、统计证据、确认卡片、任务轨迹与交易回执。
- 合成用户切换、确定性种子数据、受限管理员重置与故障演示入口。
- 后端会话归属校验、不可变操作参数、确认有效期、幂等、事务与审计。
- `mock` 和真实模型两种运行模式；前者独立可用，后者需要有效 API 配置。
- 自动化业务测试、Agent 任务集、浏览器端到端验收、启动文档与演示脚本。

### 2.2 主线完成后的 P1

- 消费趋势图、界面细节、快捷问题、评估结果展示。
- 简单规则提示，例如“大额转账”，同时展示阈值和依据。
- 更丰富的表达改写、错误提示与演示讲解材料。

### 2.3 明确不做 P2

真实资金、真实身份认证、生产级风控、真实盗刷裁决、证券或理财交易、订阅代扣管理、跨币种、手续费、异步清算、定时自动转账、批量转账、一次任务多个写操作、自动撤销已完成转账、语音、RAG、长期记忆、多 Agent、复杂模型训练。

不支持的指令应说明范围；可以建议拆成独立任务，但不得擅自执行其中一部分写操作。

## 3. 页面与交互约定

### 3.1 主页面

桌面端采用对话与任务区、账户与证据区的双栏布局；窄屏上下排列。至少包含：

1. 全局栏：演示用户、演示日期、运行模式及“合成数据 / 模拟银行”标识。
2. 对话区：用户输入、必要追问、基于工具结果的解释。
3. 任务区：已完成、处理中、等待确认、跳过、失败等真实步骤状态。
4. 业务区：账户余额、卡片状态、消费统计及可展开证据。
5. 操作区：待确认操作单、确认/取消按钮、过期倒计时、交易回执。

刷新页面后从服务端恢复任务和操作单；前端本地缓存不是业务状态的最终依据。初版采用普通请求与活动任务轮询，不强制实现流式传输或 WebSocket。

### 3.2 确认卡片

所有内容由服务端操作单生成，至少展示动作、演示用户、目标、金额和币种、账号或卡号尾号、操作影响、有效期与确认状态。本人转账同时显示来源和目标账户；条件任务增加统计区间、当前条件值及“确认时会重新核对条件”。

冻结操作说明：本模拟系统将拒绝该卡的新模拟消费；账户余额不变，账户转账不因此停用。解冻只将卡片恢复为可进行模拟消费，不代表真实银行解冻。

用户输入“确认”“好的”“帮我直接操作”时，助手引导使用对应按钮，不调用提交路径。用户修改金额、对象或条件时，先使旧操作单失效，再澄清或生成新操作单。

### 3.3 演示用户与管理员

演示用户选择只用于本地模拟，不是登录或实名认证。后端根据会话确定当前用户；业务接口不接受客户端自行指定执行用户。

重置、调整演示日期、注入故障或并发变更只能从开发测试接口或管理员入口使用，默认仅本地开放并校验管理员配置；不得注册为 Agent 工具。重置生成新的 `dataset_version`，使旧会话和旧操作单失效。

## 4. 统一业务与统计口径

### 4.1 金额、余额、额度

- 数据库和业务工具统一使用整数分；500 元对应 `50000`。货币输入通过十进制定点转换，拒绝超过两位小数、非正转账金额、布尔值和超界整数。
- 币种固定为 CNY；请求其他币种时明确不支持，不进行汇率换算。
- 余额不得小于零。本版不模拟授权占款，可用余额等于账面余额。
- 演示默认单笔转账限额为 5,000 元、每付款账户每日转出限额为 10,000 元；两类转账共同累计，失败与取消不计入。配置与测试固定这些演示阈值，不声称为真实银行规则。
- 每日统计按演示业务日期；确认时重新核对当日已成功转账金额，并在同一事务内更新，防止并发绕过。
- “转账目的”为可选备注；未提供时不追问，不作为阻断条件。

### 4.2 时间与演示时钟

使用 `Asia/Shanghai` 作为业务展示时区。持久化时间统一采用带明确时区含义的 UTC 时间，业务查询将本地日期边界转换成 UTC。

区分两种时钟：

| 时钟 | 用途 | 规则 |
| --- | --- | --- |
| 业务演示日期 `demo_date` | “本月”“昨晚”、日额度、演示交易日期 | 默认 2026-09-24；重置后固定，不随电脑日期漂移 |
| 实际系统时钟 `system_now` | 会话、确认有效期、请求耗时、审计记录 | 持续推进；测试可注入假时钟 |

演示中新业务记录使用演示日期对应的业务时间，另存真实创建时间；同日排序以业务序号辅助，不依赖时间戳唯一性。冻结演示日期不意味着确认永不过期。

默认“本月”按日统计，包含演示当日，区间为 `[当月1日00:00, 演示日期次日00:00)`。种子数据不生成演示日期之后的已入账业务。

“昨晚”默认指演示日期前一天 18:00 至演示当日 06:00；查询前在界面显示解析后的区间。用户指定其他时间时按其明确范围查询，无法确定则追问。所有查询区间统一左闭右开。

### 4.3 消费统计

| 项目 | 固定规则 |
| --- | --- |
| 数据范围 | 默认全部本人账户；必须展示选定账户和区间 |
| 消费 | 仅统计已入账的 `purchase`，金额为正整数分 |
| 退款 | 已入账 `refund` 按退款入账日扣减，关联原消费，继承原类别 |
| 净消费 | 消费总额减退款总额；允许负值并解释为当期退款超过消费 |
| 内部/外部转账、收入 | 不计入消费，也不自动推断为某一消费类别 |
| 待入账、撤销 | 不进入余额与净消费；撤销发生在入账前，已入账冲回以退款记录表达 |
| 未知类别 | 单列“未分类”，不让模型猜类别 |
| 笔数 | 消费笔数与退款笔数分别返回，避免混称交易数 |
| 默认同比较 | 本月至演示当日，对比上月1日至对应日期；上月无对应日期时取月末 |
| 上月整月比较 | 用户明确要求时使用，并注明两个区间长度可能不同 |
| 金额变化 | 本期净消费减基准期净消费 |
| 百分比 | 仅基准净消费大于零时计算；为零或负数时返回空值和原因 |
| 百分比展示 | 后端计算，按十进制四舍五入保留一位小数；不让模型重算 |
| 完整覆盖且无交易 | 返回零消费、零笔数 |
| 数据不完整或超出覆盖范围 | 标记 `incomplete`，可显示已知小计，不宣称完整总额或计算比较百分比 |

证据输出包含消费 ID、退款 ID、统计口径版本和数据版本。聚合应针对完整匹配数据，不只统计列表当前页；证据列表允许分页并返回总数。

### 4.4 转账与记账

目标为严格互斥结构：`own_account` 需要 `account_id`；`saved_recipient` 需要 `recipient_id`。拒绝同时提供两类目标；拒绝来源与目标为同一账户。

**本人账户间转账：** 校验两端为当前用户的正常 CNY 账户；一个事务内扣减来源、增加目标、递增双方版本、写入转账单和两条关联流水。两条流水共用业务编号，余额变化之和必须为零。

**预置收款人转账：** 收款人必须属于当前用户且可用；一个事务内扣减来源、递增版本、写入转账单与一条出账流水。收款人不是本系统中另一个演示用户的账户；不更新其他用户余额，不宣称收到真实银行到账确认。回执显示“模拟转账成功”。

不实现完整银行总账。外部转账用来源出账与转账单进行核对；内部转账额外验证两端守恒。每个账户满足：

`当前余额 = 期初余额 + 全部已入账贷记金额 - 全部已入账借记金额`

期初余额只用于账本初始化，不作为消费流水。种子和每次业务测试均按此公式核对；退款必须引用原消费，同币种且累计退款不超过原消费金额。

### 4.5 卡片状态

卡片状态仅 `active`、`frozen`。`active → frozen` 和 `frozen → active` 均需新确认；已处于目标状态时直接返回当前状态，不创建无意义的写操作。

卡片冻结只影响该卡的新模拟消费，不修改账户状态、不改变余额、不阻断独立账户转账，也不阻止已发生消费的退款入账。卡片与账户必须属于同一用户。

## 5. 四类场景的完整流程

### 5.1 账单分析

输入示例：“这个月餐饮花了多少，比上个月多吗？”

流程：解析日期和范围 → 展示默认口径 → 后端聚合 → 返回金额、比较结果和证据 → 解释并允许展开流水。

必备异常：非法日期、覆盖不完整、完整覆盖但无消费、基准为零或负数、退款跨月、用户请求不支持币种。

### 5.2 智能转账

输入示例：“从活期给张三转 500 元。”

流程：解析来源、目标、金额 → 查询本人账户与收款人 → 消除同名或多账户歧义 → 后端准备固定操作单 → 按钮确认 → 重新校验并提交 → 回执与余额同步更新。

缺少金额或无法唯一确定对象时必须追问，不能根据“最常用联系人”猜测。任何扣款前都应可取消。

必备异常：同名、余额不足、账户停用、超额、金额非法、过期、取消、改参、确认期间余额变化、重复/并发提交、响应丢失。

### 5.3 卡片管理

输入示例：“卡可能丢了，帮我临时冻结。”

流程：查询本人卡片 → 多卡时选择目标 → 展示尾号与影响 → 按钮确认 → 模拟冻结 → 展示实际卡状态。

不从“我不认识这笔交易”推断确定盗刷，不承诺追回资金。解冻采用同样流程；如展示身份确认，只能明确标注为模拟步骤，初版不增加独立身份验证系统。

### 5.4 跨场景 A：陌生消费与卡片处理（主演示）

输入示例：“昨晚有笔不认识的消费，帮我查是哪张卡；如果是尾号 1234，帮我临时冻结它，再告诉我账户可用余额。”

1. 解析并展示“昨晚”的时间范围，查询本人流水。
2. 有多个候选时，展示商户、金额、时间、卡片尾号，要求用户选择；不能自动判定哪笔陌生。
3. 用真实 `card_id` 关联选定交易；尾号仅作展示与条件匹配，不能作为唯一业务主键。
4. 程序检查尾号条件；不满足时跳过冻结，说明原因。
5. 满足条件时生成该卡冻结操作单，等待按钮确认。
6. 确认后复核目标、交易关联与卡片状态，执行冻结。
7. 查询所选交易关联账户的可用余额，汇总证据、冻结结果和余额。

用户仅取消冻结操作时，可以继续其已经要求的独立余额查询；用户取消整个任务时停止后续步骤。冻结失败后允许继续余额查询，但必须清楚展示冻结失败，不能用余额查询成功覆盖它。

### 5.5 跨场景 B：条件消费与本人转账

输入示例：“如果本月餐饮超过 500 元，就从活期转 100 元到储蓄账户。”

条件转换为受限结构：统计类型、账户范围、类别、固定日期区间、`gt` 比较符和 `50000` 分阈值。转账金额为 `10000` 分，来源与目标使用校验过的账户 ID。

准备阶段先统计；条件不成立时以“条件不满足，无需转账”完成任务。成立时生成操作单并展示依据。条件不是由模型输出一个布尔值来决定，也不能执行模型生成的任意表达式或代码。

确认时在同一数据库事务内重新查询当前已入账数据并判断原条件。区间沿用准备时的固定区间，数据采用执行时现状：

- 仍成立且账户版本等校验通过：执行原金额、原目标的转账。
- 条件不成立或数据覆盖不完整：操作单失效，不扣款，显示新统计值和原因。
- 条件仍成立但账户版本变化：旧操作单失效，重新展示当前数据并要求新确认。
- 用户改变条件、金额或目标：旧操作单失效，重新准备。

不在未来持续监控条件，不自动预约转账；本功能只处理当前任务的一次判断与执行。

## 6. 确认授权、幂等与事务边界

### 6.1 操作单及凭据

操作单由后端生成，固定：用户、会话、任务、动作、来源与目标 ID、金额与币种、条件结构、相关资源版本、数据集版本、统计口径版本和实际过期时间。规范化参数计算摘要，创建后参数不可改写。

确认凭据由服务端生成并仅通过会话绑定的 UI 接口交给前端；数据库保存凭据摘要。凭据不进入模型工具返回、对话记录、URL 或普通日志。它是本地演示确认协议的一部分，不宣称能证明真实持卡人身份。

确认请求只发送操作单 ID 和凭据，不发送可覆盖原金额、目标或条件的字段。服务器校验当前会话、归属、来源保护、凭据、数据集版本、状态和有效期；使用同源请求及 CSRF 防护，不向任意跨域来源开放确认接口。

### 6.2 提交顺序

1. 校验会话及操作单归属；未授权者不能获知业务结果。
2. 若该操作单已成功执行，返回已保存的原始结果，不再次检查为新业务、不再次扣款；已消费凭据不能授权另一单。
3. 若仍待确认，校验凭据、取消/过期/失效状态与固定参数完整性。
4. 开启短数据库写事务，重新读取操作单并复核授权及当前状态。条件任务先检查数据覆盖与原条件，条件不成立时返回新统计依据；条件成立后再核对资源版本、余额和额度。SQLite 实现采用可串行化写入的事务方式，例如 `BEGIN IMMEDIATE`，事务中不请求模型或网络。
5. 合法则原子更新余额或卡状态，保存业务单、流水、操作单已执行状态、步骤结果和成功审计事件。
6. 事务提交后向前端返回固定回执；如需模型解释，模型只能在提交之后生成解释。

成功结果按操作单 ID 唯一；业务表设置操作单唯一约束，避免同一操作单产生第二笔业务。幂等键由后端绑定操作单和动作，不能仅依赖前端防抖或用户随意生成的键。

### 6.3 失效与竞争规则

- 确认有效期为实际时间 5 分钟；过期只允许重新准备，不延长原单。
- 用户切换、数据重置、业务参数修改、目标资源版本变化使未执行单失效。
- 余额变化即使仍然充足，也要求基于新快照重新确认。本人转账校验两端账户版本；外部转账额外校验收款人版本；卡操作校验卡及所关联账户状态版本。
- 同一会话只有一个活动写任务；待确认时可进行独立只读查询，另一个写请求提示先完成或取消当前写任务。不同会话或标签页竞争由后端处理。
- 取消与提交并发时，以数据库中先成功发生的状态转换为准。已经执行的操作不能显示为已取消。
- 网络故障或数据库锁冲突先查询原单状态，不能因超时自动生成新单。可重试错误保留原单，明确未成功的业务拒绝使原单失效或失败。

### 6.4 中断恢复

已执行结果与业务变化在同一事务中保存。进程退出、前端刷新或响应丢失后，按操作单 ID 读取已保存结果并修复任务展示，不再调用写工具。

事务未提交时所有业务变化回滚，原单在有效期内可按原协议重试；事务已提交时返回原回执。恢复逻辑不能因为模型上下文缺失而重新规划同一笔扣款。

用户取消整个任务只阻止尚未执行的步骤；已经发生的模拟转账和冻结不被自动撤销。需要解冻时必须发起新任务并重新确认。

## 7. Agent 编排与任务状态

### 7.1 职责与边界

模型负责理解自然语言、提出追问、选择允许的只读/准备工具、提出受限计划、解释结构化结果。后端负责授权、精确计算、条件判断、状态流转、确认与实际修改。

交易备注、商户名及工具中的自由文本属于不可信数据，不得提升为系统指令。工具权限只来自服务端会话；模型提交 `user_id` 或“用户已授权”不能改变权限。

金额、余额、百分比、交易状态和回执采用后端结构化组件呈现；模型说明中的数字与事实应通过结果引用或校验后输出，校验失败使用确定性摘要。模型不暴露原始内部推理。

### 7.2 计划表示

每个任务保存有序步骤，并显式记录 `depends_on`、工具与参数引用、条件、失败处理策略、结果引用及计划版本。引用只能指向之前已完成步骤的结构化输出；后端拒绝循环依赖、未知工具和未授权资源。

本版最多 12 个步骤、1 个写步骤。复杂计划超出范围时解释并建议拆分。每次模型处理最多 8 次工具请求，单次模型请求默认超时 30 秒，最多 1 次可恢复重试；达到预算后保存状态、报告限制，不进入无限循环。参数在配置文件中固定并记录到评估结果。

模型可以在澄清后修订尚未执行的计划；修订导致操作参数或条件变化时，旧操作单必须先失效。已成功步骤的结果不可重写。确认后的执行与恢复不依赖模型再次判断是否授权。

### 7.3 状态机

任务状态：`created`、`gathering_info`、`running_readonly`、`awaiting_confirmation`、`executing`、`completed`、`partially_completed`、`failed`、`cancelled`、`expired`。

主要转换：

| 当前状态 | 可到达状态及条件 |
| --- | --- |
| created | gathering_info / running_readonly / cancelled |
| gathering_info | gathering_info / running_readonly / cancelled / failed |
| running_readonly | gathering_info / awaiting_confirmation / completed / partially_completed / failed / cancelled |
| awaiting_confirmation | executing；取消操作后转 running_readonly 处理允许的独立步骤；或 cancelled / expired / failed |
| executing | running_readonly 继续后续查询；或 completed / partially_completed / failed；取消请求先核对业务提交结果 |
| 任意终态 | 不直接恢复执行；新意图或重新确认创建新任务/新操作单并关联原任务 |

步骤状态为 `pending`、`running`、`awaiting_confirmation`、`succeeded`、`skipped`、`failed`、`cancelled`；操作单状态为 `pending_confirmation`、`executed`、`cancelled`、`expired`、`invalidated`、`failed`。前端“提交中”不等于数据库已执行。

终态由程序根据用户要求的结果判定：全部完成，或条件不满足且合法跳过，为 `completed`；部分要求已完成、其他要求失败或取消，为 `partially_completed`；仅执行了准备查询而核心动作失败，不能称为部分成功；未产生业务写入且整个任务被用户取消，为 `cancelled`。过期且未取得任何用户要求的独立结果，为 `expired`。

步骤必须明确 `on_failure=stop` 或 `continue_independent_readonly`。本版禁止失败后自动转向另一项写操作；所有终态均附带逐项结果，不能只输出一个笼统成功标志。

## 8. 业务工具与应用接口

### 8.1 模型可用工具

所有工具使用严格 JSON 参数模式，拒绝多余关键字段；输入不含可指定身份的 `user_id`。结果包含结构化状态、数据、错误码和证据引用。

| 工具 | 输入要点 | 输出及约束 |
| --- | --- | --- |
| list_accounts | 当前会话 | 本人账户、余额、币种、状态、版本 |
| list_transactions | 时间、账户/卡、类别、分页 | 本人流水、关联对象、总数、覆盖范围 |
| summarize_spending | 日期范围、账户范围、类别、比较区间 | 后端金额、笔数、比较、覆盖标记、证据与口径版本 |
| list_recipients | 姓名关键词 | 本人预置收款人 ID、姓名、尾号、状态、版本；保留同名 |
| list_cards | 当前会话 | 本人卡片 ID、尾号、关联账户、状态、版本 |
| prepare_transfer | 来源、互斥目标结构、整数金额、可选备注、可选受限条件 | 不扣款；后端验证并创建操作单，返回可展示摘要，不返回确认凭据 |
| prepare_card_action | 卡 ID、freeze/unfreeze、可选关联交易条件 | 不改状态；创建操作单或返回已处于目标状态 |
| get_task_status | task_id | 本人任务、步骤、操作单状态及结果 |

准备工具在同一任务及相同规范参数下复用现有待确认单，避免模型重试制造多份操作单。取消、失效或过期后的单不能被自动复活。

### 8.2 仅应用后端可用的执行路径

`commit_transfer`、`commit_card_action` 是确认接口后的领域服务，绝不注册到模型工具清单。取消任务/操作单、获取 UI 确认凭据、重置数据也通过专用应用接口处理。

建议接口：

| 接口 | 用途 |
| --- | --- |
| POST /api/demo/session | 选择演示用户并建立新会话 |
| GET /api/accounts、/cards、/transactions、/spending | 只读业务与证据 |
| POST /api/tasks | 创建任务及首条用户消息 |
| POST /api/tasks/{id}/messages | 提交澄清或修订指令 |
| GET /api/tasks/{id} | 恢复任务、步骤及执行结果 |
| POST /api/transfers/prepare | 表单准备转账；与工具共用领域服务 |
| POST /api/cards/{id}/actions/prepare | 表单准备卡操作；与工具共用领域服务 |
| GET /api/proposals/{id} | 获取本人操作单展示内容 |
| POST /api/proposals/{id}/confirmation-token | 获取会话绑定的 UI 确认凭据，响应禁止缓存 |
| POST /api/proposals/{id}/confirm | 校验并提交固定操作 |
| POST /api/proposals/{id}/cancel | 取消未执行操作单 |
| POST /api/tasks/{id}/cancel | 取消整个任务尚未执行的工作 |
| POST /api/admin/reset | 本地管理员重置，不提供给 Agent |

接口名称可在 M0 调整一次并记录；语义与权限不能省略。表单准备同样建立服务端任务上下文，受活动写任务限制，不能绕过对话任务的控制。

### 8.3 响应与错误

统一返回 `status`、`data`、`error_code`、`message`、`request_id`；HTTP 状态码与业务结果保持一致。确定性业务失败不做模型重试。

错误码至少包括：`INVALID_INPUT`、`UNSUPPORTED_CURRENCY`、`RESOURCE_NOT_FOUND`、`SESSION_EXPIRED`、`INSUFFICIENT_FUNDS`、`LIMIT_EXCEEDED`、`STALE_RESOURCE`、`PROPOSAL_EXPIRED`、`PROPOSAL_CANCELLED`、`CONFIRMATION_INVALID`、`CONDITION_NOT_MET`、`DATA_INCOMPLETE`、`ACTIVE_WRITE_TASK_EXISTS`、`RETRYABLE_CONFLICT`、`MODEL_UNAVAILABLE`。

跨用户资源访问采用一致的拒绝响应，不泄露其姓名、余额或是否存在。内部堆栈、密钥和确认凭据不进入返回消息。

### 9.2 合成数据规模

- 至少 3 名演示用户，每人至少 2 个 CNY 账户、2 张卡和若干预置收款人。
- 连续覆盖不少于 3 个月；默认种子覆盖 2026-06-01 至 2026-09-25 00:00（不含右端）。
- 包含工资、餐饮、购物、交通、未分类、退款、内部转账、外部转账、待入账和撤销样例。
- 包含两个“张三”、停用账户、已冻结卡、无消费但覆盖完整的账户、覆盖缺口样例、未分类与提示注入文本样例。
- 随机扩展数据使用固定种子；主演示关键交易使用固定 ID 和金额，避免随机变化破坏讲解。

### 9.3 主演示固定样例

以下仅为种子契约，开发时生成真实记录并用测试核对，不可直接用前端常量冒充查询结果。

| 项目 | 固定预期 |
| --- | --- |
| 主用户默认活期余额 | 10,000.00 元 |
| 主用户默认储蓄余额 | 20,000.00 元 |
| 本月餐饮消费 | 1,250.00 元 |
| 本月餐饮退款 | 50.00 元 |
| 本月餐饮净消费 | 1,200.00 元 |
| 上月对应日期餐饮消费/退款/净消费 | 900.00 / 100.00 / 800.00 元 |
| 默认比较结果 | 增加 400.00 元，增加 50.0% |
| 陌生消费线索 | 昨晚 21:10、88.00 元、卡尾号 1234；只标记为用户待核对线索 |
| 本人转账示例 | 活期转储蓄 100.00 元后，余额分别 9,900.00 / 20,100.00 元 |
| 外部转账示例 | 重置后给选定“张三”转 500.00 元，活期余额为 9,500.00 元 |

本月餐饮样例应含一笔 1,000.00 元原消费及其 50.00 元退款，便于在测试中再追加合法的 800.00 元退款，将净消费降为 400.00 元以验证条件失效。退款注入仅用于测试或管理员演示，不提供给 Agent。

期初余额根据固定账本构造并校验，保证所有账户当前余额与流水相符；种子不能先生成无关流水再强行覆盖余额。不同演示脚本各自重置，或明确给出相互独立的状态前置条件。

更换演示日期时，种子日期按相对月份/日期生成；月末进行合法日期截断，重新计算覆盖范围。固定金额和关键相对时间保持可核对。

## 10. 技术架构与运行约定

### 10.1 技术栈

- 前端：React、TypeScript、Vite；业务组件优先，图表库在需要时选用。
- 后端：Python、FastAPI、Pydantic；同步领域服务起步，避免混用不必要的异步数据库模式。
- 数据：SQLite、SQLAlchemy、Alembic；本地单后端进程为目标环境。
- 测试：pytest 负责领域/API/恢复测试，Playwright 负责浏览器关键流程；真实模型评估使用独立运行器。
- 模型：一个可配置的工具调用提供方；`MODEL_PROVIDER`、`MODEL_NAME`、`MODEL_BASE_URL`、`MODEL_API_KEY` 由环境配置。实际 SDK 与具体模型在 M1 技术验证后记录，不预设未验证的兼容性。
- 启动：优先支持当前 Windows PowerShell 环境；不要求 Docker、云数据库或公网服务。

M0 记录本机 Python/Node 版本，在验证后固定依赖范围与锁文件。此文不指定未经验证的最新版本，不采用漂浮依赖保证可复现。

### 10.3 模型模式

`mock` 通过有限解析器与预置场景适配器调用同一套工具、领域服务和任务状态机，不直接修改数据库，不绕过确认，不返回假交易结果。无法理解输入时明确能力范围。

`live` 调用真实模型；超时或额度不可用时返回明确失败并保留已有结果，不静默伪装为模型成功。允许用户显式切换到 `mock`，同时记录模式变化。真实模型失败不得影响已经完成的模拟银行业务。

### 10.4 预定命令契约

以下脚本是开发交付要求，目前写入方案不表示脚本已经存在。Codex 必须在对应阶段实现、实际运行并记录输出，不得只在 README 中列出。

```powershell
# M1 起：安装本地依赖，使用项目独立 Python 虚拟环境
.\scripts\setup.ps1

# M1 起：启动前后端；能检查端口冲突并清理自己启动的进程
.\scripts\dev.ps1 -Mode mock

# M1 起：初始化/重置合成数据；拒绝操作非本项目数据库

# M7 起：全部确定性验收；不依赖真实模型 API
.\scripts\check.ps1 -Stage All
```

## 11. 必须保持的系统不变量

1. 模型可见工具中不存在直接业务提交函数或确认凭据。
2. 任何余额/卡状态修改都有对应的有效确认、业务结果和审计证据；种子、测试及管理员操作另行标识。
3. 同一操作单最多产生一次业务效果，多次返回可复用同一个成功回执。
4. 本人转账两端同事务变化；任一步失败均不产生半笔转账。
5. 账户余额可用期初余额与已入账流水核对，内部转账金额守恒。
6. 用户不能读取或修改其他用户的账户、卡、收款人、任务、操作单、证据和回执。
7. 消费统计与百分比来源于后端完整数据，覆盖不足不输出完整结论。
8. 条件写操作执行前重新判断固定条件，条件变化不能被旧模型结论覆盖。
9. 前端成功提示必须对应持久化成功结果；超时、取消和失败不能显示为成功。
10. 任务恢复不能重复执行已提交写操作；用户改口和重置不能复活旧操作单。

不变量相关测试发现失败即停止扩展功能，先修复。界面美化或模型表现不能抵消业务不变量失败。

## 13. Agent 评估与用户价值验证

### 13.1 任务集

至少 40 条人工编写任务：账单 8、转账 10、卡片 8、两类跨场景合计 10、不支持/注入/恢复等边界 4。每类按相同任务结构准备正常与异常分支。

至少 30 条用于开发集，10 条留作保留集；保留集运行前不用于提示词调优。若根据保留集失败修改提示词，该集不再被表述为未见测试集，需补充新的保留样例。

每条记录：`case_id`、场景、种子/初始状态、用户输入、后续澄清和按钮事件、预期工具/约束、预期最终数据、禁止行为、通过判定。正常任务与应拒绝任务都按是否符合预期计分，不把拒绝算作天然失败。

### 13.2 指标与门槛

| 指标 | 计算/报告规则 | 门槛 |
| --- | --- | --- |
| 未经确认写入 | 没有有效操作单确认的业务修改次数 | 必须为 0 |
| 重复业务效果 | 同一操作单产生多次扣款/状态修改次数 | 必须为 0 |
| 金额与统计正确性 | 与精确预期对比，包含拒绝和空值语义 | 确定性业务测试必须全部通过 |
| 工具选择正确率 | 按允许的等价工具路径评估，不要求固定措辞 | 记录基线与改进，不预填成绩 |
| 端到端任务通过率 | 满足该样例全部预期条件的任务数/总任务数 | mock 固定演示必须全通过；live 报告实际值 |
| 状态报告一致率 | 对照数据库检查模型和 UI 的执行结论 | 参演脚本必须完全一致；全任务集报告实际值 |
| 延迟与成本 | 完整任务耗时、模型调用数、token、可获得的实际费用 | 报告中位数与范围；确认等待时间单列 |

真实模型的 40 条任务至少完整运行一次；选取关键场景与歧义场景共 10 条各运行 3 次，用于观察波动。记录每次结果，不只保留最好一次。参演脚本至少连续 3 次成功；不代表全部自然语言任务达到同样可靠性。

如果真实模型配置受阻，确定性工程验收可以继续，但 M4/M7 对应 live 验收标为受阻，不能宣称整个项目已经完成或已经验证真实 Agent 能力。

评估产物记录代码版本或文件摘要、种子版本、规则版本、模型配置、提示词摘要、模式、时间、每例通过情况与失败原因。`mock` 和 `live` 分表报告。

### 13.3 使用价值对照

基线使用同一套后端的基础表单与查询面板，避免为了对照另造完整银行 App。选择“同名转账”“陌生消费处理”“条件转账”三个任务，对比表单流程和 Agent 流程。

若能招募 5—8 名试用者，采用两种流程交替顺序、等价但不同的样例，减少学习顺序影响。记录完成率、完成时间、页面切换/输入次数，以及用户是否能正确说出最终执行结果。

只能做开发者自测时，标记为流程试验，不能写成用户研究结论；小样本结果按实际样本量报告，不做泛化的效率承诺。用户调研不阻塞核心开发。

## 14. 演示与答辩材料

### 14.1 标准演示顺序

规划约 5 分钟讲解脚本；实际时长根据核验后的赛事要求调整。

1. **约 30 秒：问题与范围。** 展示演示用户、日期、运行模式，说明全程是合成数据与模拟银行。
2. **约 60 秒：看懂开支。** 展示 1,200 元净餐饮支出、上月同期 800 元、增长 50.0%，展开消费和退款证据。
3. **约 120 秒：主演示。** 查询陌生消费，定位卡尾号 1234，展示冻结确认，执行后查询余额并展示卡状态和任务轨迹。
4. **约 60 秒：条件转账。** 重置到该脚本初始状态；演示条件成立后转入储蓄，并展示双方余额和成对流水。
5. **约 30 秒：证据与价值。** 展示幂等、故障恢复和任务集的实际结果，说明尚未覆盖的能力。

同名收款人转账、取消确认、条件被退款改变、响应丢失后恢复作为备用演示，每条有独立重置命令和检查项。现场不临时编造未测试过的成功数据。

- `docs/DEMO.md`：脚本、输入、按钮步骤、初始数据、预期结果、重置与故障恢复办法。
- `docs/EVALUATION.md`：评估方法、实际结果、失败案例、版本与复现命令。

### 15.2 M0：将方案变成可执行开发基线

**目标：** 明确当前环境、约束与工作记录，避免开发从隐含假设开始。

**Codex 任务：**

1. 检查仓库/目录、适用指令、已有文件和未提交修改；保留两版方案。
2. 检查 Python、Node、npm 和可用终端；记录版本与缺失项，不自动执行全局升级。
3. 建立 `docs/DEVELOPMENT_STATUS.md`，记录当前阶段、任务清单、阻塞项和下一步；所有阶段初始为未开始。
4. 建立 `docs/DECISIONS.md` 和 `docs/BUSINESS_RULES.md`，将本文已定规则转为简明实现契约；具体数据结构命名可定稿，不能改变业务语义。
5. 建立 `docs/COMPETITION_CHECKLIST.md`：官方来源、核验日期、报名资格、赛道要求、交付形式、截止时间、指定平台、合成数据是否允许。没有资料时标“待核验”，禁止猜测。
6. 建立 API 草案和阶段测试映射，确定包管理方式、目录、数据库路径与配置键；暂不搭建全部功能。
7. 依据可用人力与时间调整参考排期；未获知的人力、预算写为外部未决，不自行虚构姓名或金额。

**交付物：** 开发状态、决策记录、业务规则、赛事核验清单、API 草案。

**验收：** 逐项核对金额、时间、统计、转账、确认、条件复核、模式标识及状态机均有唯一可执行定义；原版文件保持不变；环境可支撑 M1，或已明确可恢复的缺失项。

**进入 M1 的条件：** 内部产品与工程基线明确。赛事信息缺失不阻塞可逆的本地模拟原型，但必须持续标记，不能据此宣布报名合规或开始外部提交。

### 15.3 M1：可启动骨架、合成数据与只读路径

**目标：** 从干净环境启动后，可以选择用户并看到真实数据库中的账户、卡片和流水。

**Codex 任务：**

1. 初始化后端应用、配置、健康检查、SQLite 连接、迁移和前端；固定依赖并写环境示例。
2. 实现用户、会话、设置、账户、卡片、收款人、流水和覆盖范围的基础模型；启用外键及必要约束。
3. 实现固定种子与安全重置脚本，建立期初余额核对；重置只针对本项目数据库，生成新数据版本。
4. 实现演示用户会话和只读接口；客户端不能通过更换资源 ID 跨用户查询。
5. 实现基础页面：模式/日期标识、用户选择、账户余额、卡片状态和分页流水；所有数据由 API 获取。
6. 实现 `setup.ps1`、`dev.ps1`、`reset-demo.ps1` 与 `check.ps1 -Stage M1`；处理端口占用、异常退出和项目自身进程清理。
7. 新增有针对性的种子、会话隔离和只读 API 测试；验证分页不会泄露其他用户数据。
8. 建立极小模型适配试验：一次只读工具调用、一次严格参数校验、一次缺信息追问。存在有效配置时运行 live；无配置时记录待验证，不编造结果。试验不能暴露任何提交工具。

**交付物：** 可启动前后端、基础迁移、种子脚本、会话与只读 API、基础 UI、启动文档、模型适配试验记录。

**验收命令与检查：**

```powershell
.\scripts\setup.ps1
.\scripts\reset-demo.ps1 -Date 2026-09-24
.\scripts\check.ps1 -Stage M1
.\scripts\dev.ps1 -Mode mock
```

浏览器切换三名用户并检查账户与卡片隔离；两次重置后关键业务数据相同，但数据版本不同；完整性测试核对默认余额和种子账本。

**门槛：** 启动、重置、只读接口及隔离检查通过，前端构建成功。模型适配试验缺少凭据可以单独受阻，不妨碍 M2/M3；进入 M4 的 live 验收前必须解决。

**本阶段不做：** 转账提交、复杂确认 UI、正式 Agent、跨场景编排、界面精修。

### 15.4 M2：统计与账本领域规则

**目标：** 不依赖模型即可得到准确统计，并具备统一的账本与业务校验服务。

**Codex 任务：**

1. 实现整数分输入校验、十进制转换、账户归属和状态校验、演示时钟与实际时钟抽象。
2. 实现流水记账与余额核对服务，统一消费、退款、收入、转账及无效记录的处理；业务写方法暂不暴露给公共 API。
3. 实现退款关联、累计退款上限、内部转账配对及日额度查询规则。
4. 实现 `summarize_spending`，覆盖退款、跨月、区间边界、月末截断、覆盖缺口、零/负基准与未分类。
5. 实现统计 API 与可展开证据；聚合完整数据，证据分页。
6. 界面提供基本日期/类别查询和结构化结果，模型尚未接入也可使用。
7. 增加 B01—B04 对应测试，及金额、退款和基础领域规则测试；写入明确的手算预期值，避免测试重复调用实现计算“预期”。

**交付物：** 领域金额/账本/统计服务、统计 API、证据界面和测试。

**验收命令：** ` .\scripts\check.ps1 -Stage M2 `。

**人工核对：** 默认餐饮净消费 1,200 元，上月对应日期 800 元，差额 400 元，增长 50.0%；证据中退款被正确扣减，内部转账不计入消费。

**门槛：** B01—B04 及领域规则测试全部通过；证据可以解释每个金额；不完整数据与零交易具有不同返回语义。

**本阶段不做：** 对公众可用的裸写接口、LLM 计算金额、模型推测交易类别。

### 15.5 M3：确认与真实模拟业务闭环

**目标：** 通过基础表单和按钮完成可恢复、可核对的转账与卡片操作，全程不依赖 LLM。

**Codex 任务：**

1. 添加操作单、业务单、任务最小记录与审计模型及迁移；实现不可变参数快照和资源版本绑定。
2. 实现两种转账目标、卡动作准备接口；同任务同参数准备重试复用操作单。
3. 实现会话绑定的 UI 确认凭据、5 分钟实际有效期、取消、失效、CSRF 与严格请求字段校验。
4. 实现提交领域服务和事务边界，包含内部双端记账、外部出账、卡状态修改、业务结果及审计原子保存。
5. 实现幂等结果查询、并发竞争、余额/额度重验、资源版本变化拒绝和失败后的可重试区分。
6. 实现用户切换、重置使旧会话/旧单失效；实现活动写任务限制，表单与后续 Agent 共用限制。
7. 实现最小确认卡片与交易回执，提交中禁重复点击，但仍以服务端幂等为准；刷新从服务器恢复。
8. 添加独立连接并发测试和故障注入测试，覆盖提交前失败与提交后响应丢失；禁止故障入口出现在生产式普通工具接口中。

**交付物：** 两种转账、冻结/解冻、确认协议、回执、审计、基础表单与故障恢复测试。

**验收命令：** ` .\scripts\check.ps1 -Stage M3 `。

**验收流程：** 重置 → 表单准备本人转账 100 元 → 确认 → 核对两端余额和流水 → 重复提交 → 结果不变；分别完成外部转账、冻结/解冻、取消/过期、故障恢复。

**门槛：** B05—B15、B17 的业务层测试通过，M1/M2 必要回归通过。只有 API 文案成功、余额和流水未变化，视为失败。审计缺失或并发重复扣款时不得进入 M4。

**本阶段不做：** 用模型授权写入、自然语言“确认”提交、复杂任务计划、自动撤销已完成业务。

### 15.6 M4：三类单场景 Agent

**目标：** 用户可经对话触发账单、转账和卡片任务，歧义得到澄清，执行仍走 M3 的确认路径。

**Codex 任务：**

1. 定义提供方适配接口、严格工具 schema、错误映射、模型超时与预算；工具注册表只包含第 8.1 节允许项。
2. 实现 `mock` 适配器，复用真实领域工具；不写关键词命中后直接返回“成功”的假业务。
3. 接入一个经 M1 验证的 live 提供方，密钥仅来自环境；模型选择和配置写入决策记录。
4. 实现单场景对话上下文、任务消息、缺信息追问和明确对象选择；同名收款人由用户选择 ID 对应对象。
5. 将准备结果投影到确认 UI，由按钮触发既有提交接口；模型只读取已执行回执。
6. 实现用户改口使旧单失效、聊天确认仅提示按钮、工具结果数字引用校验和确定性摘要回退。
7. 实现注入边界测试、越权测试、调用预算测试；模型自由文本不能改变会话身份或发起提交。
8. 建立任务集 schema 与首批不少于 20 条开发样例；实现 `evaluate.ps1` 的模式、分集、结果输出和非零失败码。

**交付物：** Agent 适配层、单场景任务、对话 UI、首批评估任务与运行器、真实模型适配证据。

**验收命令：**

```powershell
.\scripts\check.ps1 -Stage M4
.\scripts\evaluate.ps1 -Mode mock -Split dev
.\scripts\evaluate.ps1 -Mode live -Split dev
```

**门槛：** 三类单场景的正常、追问、拒绝流程均能通过对话完成；A01—A05、A09—A10 有测试证据；固定单场景脚本在 live 下完成且数字、状态正确。非核心表达失败记录到评估，不伪造全部任务通过率。

**受阻处理：** 无可用模型凭据时可完成 mock、工具与安全测试，并继续实现不依赖 live 的后续工程；M4 标“工程通过 / live 验收受阻”，不能整体标完成。不得改用假模型结果满足门槛。

**本阶段不做：** 跨场景任意规划、第二个模型提供方、自动切换模式掩盖失败。

### 15.7 M5：跨场景计划、条件复核与任务恢复

**目标：** 两条主流程能在真实工具结果驱动下暂停、确认、继续和恢复，并正确解释部分失败。

**Codex 任务：**

1. 扩展任务与步骤模型，保存依赖、计划版本、输入/结果引用、失败策略和用户要求的结果。
2. 实现受限计划解析与校验：工具白名单、有序依赖、最多 12 步和 1 个写操作，不执行任意代码表达式。
3. 实现陌生消费流程：候选交易选择、卡关联和尾号条件、冻结确认、独立余额查询及逐项汇总。
4. 实现消费条件转账：固定区间和条件结构、准备时判断、提交事务内再次判断；数据不完整时停止写操作。
5. 实现暂停持久化、刷新/重启恢复、根据业务结果修复任务状态；不将恢复交给模型重新决定是否扣款。
6. 实现拒绝某个操作与取消整个任务的区别；写成功但后续读取失败保留成功回执。
7. 实现 B16、B18 和编排层 B15/B17 测试，验证 A06—A08；包含条件由新增退款变为不成立。
8. 扩展到完整 40 条任务集，并划分开发/保留集；保留集不得混入提示词示例。

**交付物：** 状态机与计划执行器、两条跨场景流程、任务轨迹、恢复逻辑和完整任务集。

**验收命令：** ` .\scripts\check.ps1 -Stage M5 `；运行两条跨场景的 mock 与 live 开发样例。

**门槛：** 两条主故事具备成功、条件不成立、取消、失败和中断恢复证据；检查“退款改变条件后不扣款”“已成功业务重启后不重做”；终态与逐步骤真实结果一致。

**本阶段不做：** 多写操作分布式事务、任意长期计划、后台定时执行、自动补偿转账。

### 15.8 M6：界面整合与浏览器验收

**目标：** 用户可以独立完成流程；刷新、窄屏和网络错误不会造成误导性结果。

**Codex 任务：**

1. 整合对话、任务、账户、统计证据、确认和回执，减少重复信息，保证金额与目标醒目。
2. 补齐加载、空结果、不完整数据、失败、过期、取消、重试和结果恢复状态。
3. 实现页面刷新恢复、用户切换清理、活动任务轮询及停止条件；多标签页旧状态由服务器拒绝并刷新。
4. 优化确认卡片的可读性与按钮状态；保持模拟/真实模型模式和演示日期始终可辨识。
5. 补齐第 12.3 节的 Playwright 核心流程，并验证数据库实际结果；录制或保存必要失败截图供排查。
6. 做一次桌面和窄屏人工检查，检查键盘可操作性、文字截断、金额格式、滚动和错误提示。
7. 完成不依赖外部数据的消费图表；仅在不影响主线的情况下加入 P1 视觉细节。

**交付物：** 完整前端、浏览器验收测试、人工检查记录和可重复演示页面。

**验收命令：** ` .\scripts\check.ps1 -Stage M6 `，其中包含前端类型检查、构建和指定浏览器流程。

**门槛：** 所有核心浏览器流程通过；刷新或响应丢失后不会重复写入；窄屏可完成确认/取消；UI 状态均能对应后端数据。

**本阶段不做：** 以动画替代结果核对、无关页面扩张、为了视觉重构已通过验证的领域层。

### 15.9 M7：评估、复现与参赛交付

**目标：** 交付别人可复现的系统、可信评估结果和有证据的演示材料。

**Codex 任务：**

1. 运行完整确定性检查，修复影响主线的问题；没有新变化或未决问题时不无目的重复运行全套测试。
2. 分别运行 mock/live 任务集，执行保留集和关键样例重复试验，保存原始结果及失败原因。
3. 按第 13 节条件开展表单对照试验；无试用者时注明开发者自测，不编造用户反馈。
4. 完成 README：环境、安装、配置、迁移、初始化、启动、测试、重置、常见故障和模式切换。
5. 完成 DEMO、API、EVALUATION、实际架构/时序图与限制说明，确认文档命令可以实际执行。
6. 用独立临时数据库和干净依赖环境验证首次启动；不删除或覆盖用户主数据库和已有工作。
7. 主演示和备用演示各自排练；live 主演示连续 3 次通过后记录版本，准备可识别为 mock 的备用方案。
8. 复核官方要求差异并调整交付材料。外部报名、上传、公开发布另行执行，本文开发授权不自动包含它们。
9. 最终更新 `DEVELOPMENT_STATUS.md`：完成范围、实际证据、未完成项、已知风险及复现入口。

**验收命令：**

```powershell
.\scripts\check.ps1 -Stage All
.\scripts\evaluate.ps1 -Mode mock -Split dev
.\scripts\evaluate.ps1 -Mode live -Split dev
.\scripts\evaluate.ps1 -Mode live -Split holdout
```

**门槛：** P0 全部满足；确定性业务及浏览器验收通过；live 实际评估与参演脚本证据齐全；另一份本地环境能够照 README 复现。任何未通过项必须显式列出，不能用“整体基本完成”掩盖。

## 16. Codex 进度管理与交付格式

### 16.1 开发状态记录

`docs/DEVELOPMENT_STATUS.md` 至少保存：

```markdown
# 开发状态

- 当前阶段：M1
- 当前状态：进行中
- 已完成：写明有对应代码/验证证据的内容
- 正在处理：当前具体问题
- 外部受阻：无；或明确依赖与受影响验收
- 最近验收：命令、日期、通过/失败/未运行、结果位置
- 下一步：一项可直接执行的任务

| 阶段 | 状态 | 证据位置 | 未完成项 |
| --- | --- | --- | --- |
| M0 | 待填写真实状态 | docs/ACCEPTANCE/M0.md | 待填写 |
```

该段是格式示例，不能直接把示例中的 M1 视为实际开发进度。新任务接手时先读取此文件，再核对实际代码与验收证据，不能只相信状态标签。

### 16.2 每阶段交付报告

在 `docs/ACCEPTANCE/Mx.md` 记录：

1. 本阶段实现了什么，对应哪些需求和验收编号。
2. 新增/修改文件及关键设计决策。
3. 环境版本、种子版本和运行模式。
4. 实际执行命令、结果、日期及必要日志位置。
5. 手工验收步骤和实际观察结果。
6. 未通过、未运行、外部受阻和已知限制，分别列出。
7. 是否满足进入下一阶段条件，以及下一阶段第一项任务。

对用户的阶段汇报保持简明；详细过程留在文件中。遇到错误先修复，不能以“用户可以自行测试”替代已经授权且环境可执行的检查。

### 16.3 需求变更处理

仅修改内部实现、不改变行为的选择，由 Codex 自行完成并记决策；涉及范围、转账语义、确认要求、金额口径或外部费用的变化，先写清影响并按用户授权范围处理。

修改已定行为时更新本文版本、业务规则及对应测试，说明原因；不得静默削弱确认、隔离、记账或恢复要求。阶段检查失败时不通过删除断言“修复测试”。

### 16.4 可直接使用的首轮开发指令

以下是用户后续启动 M0/M1 时可使用的指令，本文编写本身不启动代码开发：

> 阅读《finagent企划方案_v2.0.md》和适用的 AGENTS.md，先检查当前文件与环境，保留两版方案和用户已有改动。完成 M0 开发基线，再实现并验收 M1：前后端启动、SQLite 迁移、固定种子、演示会话、账户/卡片/流水只读 API、基础界面和启动/重置/检查脚本。模型适配仅做小试验，暂不实现写操作或完整 Agent。实际运行可执行检查，更新 DEVELOPMENT_STATUS、DECISIONS 和 M0/M1 验收记录。遇到缺失 API 凭据继续完成不依赖凭据的工作，准确标记受阻项。最后给出运行命令、验收结果与下一阶段任务。

后续接续指令：

> 按第二版方案和 DEVELOPMENT_STATUS，从第一个未完成阶段继续。先核对现有实现和最近验收，不重做已完成工作，不跳过前置门槛。完成本次授权范围内的开发、测试和进度记录，准确列出受阻或未验证项。

## 17. 范围压缩、风险与外部未决项

### 17.1 时间不足时的删减顺序

依次删减：风险评分 → 复杂图表与动画 → 非必要视觉细节 → 额外模型提供方 → 超出基线的表达扩展。保留三类单场景、两条跨场景、固定演示、业务不变量、真实评估和可复现启动。

若仍无法完成，必须显式调整项目范围和材料主张；不能保留原功能承诺而只实现成功演示。官方最低要求核验后，删减顺序再与之对齐。

### 17.2 主要实施风险

| 风险 | 处理方式 | 出现时的验收影响 |
| --- | --- | --- |
| 模型工具调用不稳定 | M1 提前试验；严格 schema；有限重试与失败记录 | 不影响领域测试，影响 live Agent 验收 |
| 业务正确性开发超时 | M2/M3 优先；延后 P1；用小范围明确规则减少复杂度 | 未通过时停止扩展功能 |
| 演示日期漂移 | 固定业务日期、独立实际时钟、固定种子 | 日期与样例测试必须通过 |
| 网络超时造成重复业务 | 原单唯一、结果持久化、查询恢复、故障注入 | 发生重复效果即阻断交付 |
| 赛事要求与当前范围不同 | 单独核验官方材料，登记差异和变更 | 不宣称满足尚未验证的要求 |
| 评估只覆盖背熟脚本 | 表达改写、异常分支、保留集、关键任务重复运行 | 只报告实际覆盖，不夸大泛化 |

### 17.3 外部未决项

- 赛事当届官方文件、准确截止时间、报名资格、团队人数、评审维度。
- 是否必须使用指定模型、平台、API、真实接口或特定运行环境。
- 是否接受完全合成数据和本地模拟银行；提交代码、视频与文档的格式要求。
- 团队实际成员、每周可用时间、预算与可用模型凭据。
- 是否能邀请试用者完成用户价值对照。

以上不以猜测补齐。工程内部规则已经由本文定稿，外部未决项通过 `COMPETITION_CHECKLIST.md` 和开发状态持续跟踪。

## 18. 最终完成定义

同时满足以下条件，才可把 v2.0 的产品开发标记为完成：

1. Windows 本地按文档可启动、重置并复现全部固定演示。
2. 三类单场景与两类跨场景均使用真实数据库、领域服务和受控确认路径。
3. 本人/外部转账、退款统计、日期、覆盖范围和卡片行为符合本文口径。
4. 权限隔离、一次确认一次效果、并发、取消、条件变化及故障恢复测试通过。
5. UI 数字、状态、证据、回执与后端一致；刷新及失败场景可正确恢复。
6. `mock` 与 `live` 标识清楚；真实模型评估已运行并记录实际结果和失败案例。
7. 任务集、浏览器验收、参演脚本重复运行和首次启动验证具有证据。
8. README、API、DEMO、EVALUATION、开发状态与验收文件完整，没有把计划写成已完成成果。

赛事报名和提交是否完成单独跟踪，不与本地产品开发完成混为一谈。
