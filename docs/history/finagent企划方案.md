## 0. 给 Codex 的执行原则

本文是产品和工程规格，不是一次性把全部功能写完的命令。按第 13 节里程碑逐阶段实现；每阶段应提供可运行系统、使用说明和验收结果，完成验收再进入下一阶段。优先保证模拟银行业务真实、数据一致、确认机制有效，再接入大模型与扩展能力。如果模型 API 不可用，基本业务接口、演示数据和确定性验收仍应可用。不要自行声称已接入真实银行、真实支付或真实身份认证。

## 1. 项目概述

**项目暂定名**：FinAgent——面向个人用户的可执行银行智能助手。

**一句话定位**：用户以自然语言表达金融目标，Agent 查询模拟账户数据、规划步骤并调用受控业务工具；涉及账户或卡片状态变更时，由后端校验并取得与具体操作绑定的确认，然后完成模拟业务。

**目标用户**：希望快速了解开支、通过对话完成日常银行操作、在异常交易或卡片问题出现时获得清晰处理路径的个人银行用户。

**参赛主张**：从“查询信息”延伸到“执行任务”，展示金融业务中可追踪、可核验、可中断的 Agent 工作流。

**范围**：三个核心场景为账单分析、智能转账、卡片管理；跨场景联动为第四个重点能力。全部使用合成数据与模拟银行 API。不处理真实资金、不采集真实卡号或身份信息，也不提供投资收益承诺。

## 2. 成功标准与范围边界

### 2.1 第一版必须做到

1. 网页端可选择演示用户，展示账户、卡片、流水和对话；后端数据变化可被界面直接观察。
2. 三个核心场景各有完整正常流程和至少两条重要异常流程。
3. 查询结果由程序从模拟数据库计算；大模型不能臆造余额、统计数值或操作成功结果。
4. 每项会修改数据的操作生成结构化待确认操作单；用户明确确认后才可执行。拒绝、过期和参数变化均不可执行。
5. 跨场景指令可以查询、暂停、等待确认、继续执行、失败停止，并展示每一步真实状态。
6. 数据库能记录用户指令、关键工具调用、确认及实际业务结果；演示界面能查看简化的操作轨迹。

### 2.2 明确暂缓

- 真实银行、真实卡片、真实资金、真实身份认证、生产级风控。
- 理财产品申购赎回、真实境外消费权限、声称可识别盗刷的自动裁决。
- 多 Agent、长期记忆、RAG、向量数据库、知识图谱、语音、复杂模型训练。
- 未完成技术验证前不把“订阅/代扣管理”列入第一版必做范围；它是后续扩展场景。

## 3. 用户体验与页面

首页为双栏或响应式布局：左侧是自然语言对话和任务进度，右侧显示账户余额、卡片状态、消费概览与待确认操作单。移动端可改为上下布局。

**任务状态**：`已理解 → 正在查询 → 已给出分析/计划 → 等待确认 → 正在执行 → 成功/部分成功/失败/已取消`。每一步显示实际执行时间、依据和结果；不显示原始模型内部推理。

**确认卡片**：必须清楚显示动作类型、用户、付款账户与尾号、收款人及尾号、金额或目标卡片、有效期、风险提示和“确认/取消”。展示的确认内容必须与实际提交到后端的参数一致。卡片管理显示目标卡号尾号及操作前后状态。

**演示辅助**：提供“重置演示数据”和预置问题按钮。重置只能用于本地演示管理员入口，不能由普通 Agent 工具调用；每次重置说明将恢复合成数据。

## 4. 核心场景规格

### 4.1 场景 A：账单分析

**示例**：“这个月餐饮花了多少？比上个月多吗？”

- 输入：时间范围、账户范围、商户或类别、比较基准；缺失时采用界面明确展示的默认值，例如当前自然月和全部本人账户。
- 工具流程：获取流水 → 排除内部转账和撤销交易等不计入消费的项目 → 按类别聚合 → 计算同比/环比所需基准 → 返回结构化数字与交易证据 → Agent 生成解释。
- 输出：消费总额、分类明细、对应交易数、比较区间、相对变化率，以及可展开的原始流水。
- 计算约定：金额以最小货币单位整数存储；同类消费金额求和。基准期为 0 时不计算百分比，改为说明“基准期为零”。退款按预先定义的净额规则处理。未知类别单列“未分类”，不得由模型虚构分类依据。
- 异常：无数据时说明无数据，不推断为零支出；日期范围非法时报错或追问；不同币种不直接相加。

### 4.2 场景 B：智能转账

**示例**：“从活期给张三转 500 元。”

1. 解析金额、付款账户、收款对象、转账目的；缺失则追问。
2. 查询用户本人账户及已保存收款人；同名收款人要求明确选择，界面仅展示脱敏账户尾号。
3. 业务后端验证币种、余额、账户状态、单笔/当日额度、收款人状态和金额合法性。
4. 生成待确认操作单并将完整参数固定；向用户展示确认卡片。
5. 用户点击确认或在明确绑定的会话内确认该操作单；后端重新校验余额、额度、版本与有效期，在数据库事务中执行模拟转账。
6. 返回交易编号、实际状态、更新后的余额和流水。网络超时或重复点击使用幂等键防止重复扣款。

**异常演示**：张三同名、余额不足、余额在确认期间变化、超额、取消确认、确认过期、重复确认、后端返回失败。所有失败路径均不能出现虚假的“转账成功”。

### 4.3 场景 C：卡片管理

**示例**：“我的银行卡可能丢了，看看是哪张卡，并帮我临时冻结。”

- 查询用户本人卡片及状态，展示品牌/别名/尾号；多张卡时要求用户明确目标。
- 支持查看状态、模拟临时冻结、模拟解冻；第一版不实现实体卡挂失、补卡、额度调整。
- 冻结前说明影响，要求绑定到指定卡片的明确确认；如果当前卡已冻结，直接告知状态，不制造重复操作。
- 解冻需再次确认且校验卡片状态。演示环境的“身份确认”只是模拟步骤，界面要标注“模拟身份校验”，不得宣称完成真实身份验证。
- 卡片操作必须返回实际状态，并留下审计记录。卡片冻结属于紧急处理场景，交互应短而清楚；不要因为主观风险分数叠加无意义步骤。

### 4.4 场景 D：跨场景联动

**主故事一：条件消费与转账。** “计算本月餐饮支出；若超过 500 元，从活期转 100 元到储蓄账户。”先调用账单统计工具，用程序判断条件；未超过则结束并说明；超过时生成转账操作单，确认后执行。

**主故事二：异常消费与卡片处理。** “昨晚有笔不认识的消费，帮我查是哪张卡；如果是尾号 1234，帮我临时冻结它，再告诉我账户可用余额。”先查流水与关联卡片，向用户展示证据；不得自行断言盗刷。条件满足时生成指定卡片的冻结确认，执行后查询余额并总结实际状态。用户拒绝或冻结失败时，如后续余额查询仍可独立执行，可继续查询，但最终汇总必须明确区分已执行和未执行步骤。

**实现要求**：每个任务拥有 `task_id`、有序步骤列表和状态；步骤可依工具结果更新计划。遇到确认点暂停并保存状态；恢复时重新取当前数据并重验业务规则。跨场景任务不允许靠一段预写的“成功回答”冒充工具执行。

## 5. Agent 编排原则

Agent 负责意图理解、补充信息、选择允许的工具、解释工具返回值与编排多步骤任务；后端负责精确计算、业务规则、权限和数据修改。第一版采用**受约束的单 Agent + 明确任务状态机**，不引入多 Agent 系统。

可用工具必须有明确 JSON 参数模式、调用者上下文与返回模式。LLM 的工具调用是“请求”，不是对数据库的授权。工具只接受由服务器会话绑定的用户身份；模型输出的 `user_id` 或账户归属信息不可作为权限依据。

**状态机**：`created`、`gathering_info`、`running_readonly`、`awaiting_confirmation`、`executing`、`completed`、`partially_completed`、`failed`、`cancelled`、`expired`。非法状态转换由后端拒绝；等待确认时保存操作单，不重复询问模型“是否已经确认”。

**不可信内容边界**：交易备注、商户名称和导入账单都视为数据，不能作为系统指令。模型遇到其中包含“忽略规则”“直接转账”等文本时仅能将其作为引用数据；工具白名单、权限及确认校验必须由程序实施。

## 6. 业务工具清单

| 工具 | 类型 | 输入 | 输出与约束 |
| --- | --- | --- | --- |
| `list_accounts` | 只读 | 当前会话 | 本人账户和余额、币种、状态；脱敏账户号 |
| `list_transactions` | 只读 | 时间范围、账户、分页 | 本人流水、关联卡、类别及交易状态 |
| `summarize_spending` | 只读 | 时间范围、类别、对比区间 | 后端计算的整数金额、笔数、证据流水 ID |
| `list_recipients` | 只读 | 关键词 | 本人已保存收款人和脱敏账号；保留重名情况 |
| `list_cards` | 只读 | 当前会话 | 本人卡片尾号、状态和关联账户 |
| `prepare_transfer` | 预备 | 来源账户、收款人 ID、金额 | 校验结果、冻结参数的待确认操作单；不扣款 |
| `commit_transfer` | 写入 | 操作单 ID、一次性确认凭据 | 重验并事务性转账，返回交易 ID；模型不能自行生成确认凭据 |
| `prepare_card_action` | 预备 | 卡 ID、动作 | 校验结果、待确认操作单；不修改状态 |
| `commit_card_action` | 写入 | 操作单 ID、一次性确认凭据 | 重验并修改卡状态；幂等 |
| `get_task_status` | 只读 | 任务 ID | 步骤状态、待确认操作和实际结果 |

`commit_*` 仅供经后端确认流程授权的执行路径使用；不把可直接提交写操作的工具暴露给自由工具调用循环。前端提交确认时只发送操作单 ID 和用户点击确认产生的一次性凭据，服务端由操作单还原固定参数。确认拒绝、会话过期、操作单过期、用户切换或卡片/账户状态变化时，拒绝提交并要求重新生成操作单。

## 7. 模拟银行数据模型

推荐 SQLite 起步，使用关系表并在需要时迁移。字段名称可按实现调整，但语义不能缺失。

| 实体 | 主要字段 | 约束 |
| --- | --- | --- |
| `users` | id、演示名称、画像 | 全部为合成用户 |
| `accounts` | id、owner_id、别名、币种、余额（分）、状态、version | 余额非负；归属校验；乐观版本 |
| `recipients` | id、owner_id、姓名、账号掩码、状态 | 同名可并存；写入时引用 ID |
| `cards` | id、owner_id、account_id、尾号、状态、version | 状态枚举；卡与账户归属一致 |
| `transactions` | id、owner_id、account_id、card_id、类型、金额（分）、币种、类别、商户、时间、状态、关联业务 ID | 退款、撤销、内部转账可被区分 |
| `transfer_orders` | id、来源/目标、金额（分）、状态、idempotency_key、created_at | 唯一幂等键；审计依据 |
| `action_proposals` | id、owner_id、task_id、动作、固定参数、参数摘要、过期时间、状态、nonce | 单次确认；确认后不可修改 |
| `agent_tasks` / `task_steps` | id、owner_id、步骤序号、状态、工具与结果摘要 | 可暂停、恢复和回放状态 |
| `audit_events` | id、owner_id、任务 ID、动作、结果、时间 | 记录请求、确认、拒绝、执行与失败 |

合成数据至少三名用户、每人两个账户、若干卡片与收款人、三个月以上的多类别流水；要包含同名联系人、退款、内部转账、卡片已冻结、超额请求和异常消费线索。所有演示数据可由固定种子脚本重建；不得把真实个人信息写入种子脚本。

## 8. 风险控制与操作确认

### 8.1 硬规则先行

任何写操作先检查资源归属、合法金额、账户/卡状态、余额、额度、操作单一致性、确认有效期与幂等性；不满足时直接拒绝。查询类工具同样按当前会话限制资源。硬规则执行在可信后端，不能只写在提示词里。

### 8.2 风险提示与可解释评分

第一版可使用清楚可审计的规则提示，例如金额高于该演示用户历史分位数、新收款人或短时间频繁转账。评分属于**展示与进一步核查线索**，不代替硬规则与确认。

数学扩展阶段可定义经归一化的特征：金额相对历史分布的分位数、近期转账频率偏离、收款人新颖度、卡片状态等；模型形式可从简单加权评分开始。权重、阈值应在合成场景上预先固定，通过正常/异常样例检验误报、漏报与阈值敏感性。展示为“基于演示规则的风险提示”，不声称预测真实金融欺诈概率。

### 8.3 确认机制的技术不变量

- 任何写操作都必须先由后端创建完整操作单；LLM 的一句“用户已经同意”无效。
- 操作单绑定当前演示用户、动作、对象、金额和会话；用户确认的是这份固定快照。
- 同一个操作单只能成功提交一次。重复请求返回相同结果或明确已执行状态，不重复扣款。
- 状态或业务参数变化后重新校验；确认过期必须重建。
- 每次执行有审计记录。前端明确区分“待确认”“执行中”“执行成功”“执行失败”。

## 9. 技术实现建议

- **前端**：React + TypeScript；实现响应式对话、账户与卡片面板、消费图表、确认卡片、任务轨迹。先做可用界面，再做视觉打磨。
- **后端**：Python + FastAPI；分业务服务、Agent 编排、数据访问和确认执行层。Python 初学者可从单个业务工具逐步理解。
- **数据**：SQLite 起步；金额以整数分存储，明确时区与日期范围；通过事务保证转账与流水同步。
- **模型**：可配置的支持结构化工具调用的 LLM API；密钥放环境变量，绝不写入仓库。提供 `mock` 模式以验证业务与演示兜底；展示时注明模拟模式和真实模型模式的差别。
- **启动**：提供一条命令启动或清晰的前后端启动步骤、数据初始化命令、环境变量示例文件。无需云服务即可运行基本业务和固定演示。

## 10. API 与业务响应约定

建议区分模型请求、只读查询、操作单准备和确认提交四类接口。所有 API 返回标准化 `status`、`data`、`error_code`、`message` 与 `request_id`；错误不直接返回内部堆栈或模型密钥。

确认操作单示意：

```json
{
  "proposal_id": "proposal_demo_001",
  "type": "transfer",
  "status": "awaiting_confirmation",
  "summary": {
    "source_account_mask": "**4082",
    "recipient_name": "张三",
    "recipient_account_mask": "**3821",
    "amount_minor": 50000,
    "currency": "CNY"
  },
  "expires_at": "2026-09-24T10:30:00+08:00"
}
```

上例为示意时间和数据；实际 ID、有效期和确认凭据由服务端生成。`amount_minor` 为人民币分。确认提交不得由前端重新传入可覆盖的金额、收款人等执行参数。

## 11. 演示脚本

准备“重置数据”后可重复运行的三段演示，每段都有可见的数据库状态变化或证据。

**第一段——看懂**：询问“这个月餐饮花了多少钱，比上个月多多少？”；展开某个统计值对应的流水，说明统计口径。

**第二段——安全地执行**：输入“给张三转 500 元”；预置两个张三，让系统追问；选定尾号后展示确认卡片并提交；观察余额和交易流水变化；再重复提交同一操作，演示不会重复扣款。

**第三段——跨场景**：输入“昨晚有笔不认识的消费，帮我查是哪张卡；如果是尾号 1234，帮我临时冻结它，再告诉我账户可用余额”；展示证据、明确用户确认、冻结状态变化与任务汇总。可再演示拒绝确认时卡片状态保持原样。

准备一段补充的消费条件转账 Demo，应对评委对自主决策与多工具协同的追问。所有脚本都必须能在 `mock` 模式重现；使用真实 LLM 时检查改写输入和追问也能完成任务。

## 12. 验收与评估

### 12.1 自动化业务验收

以下场景需要后端测试，既验证成功路径，也验证失败后状态不变：

| 编号 | 情况 | 验收结果 |
| --- | --- | --- |
| T01 | 足额转账并确认 | 余额、转账单与流水一致；只执行一次 |
| T02 | 同名收款人 | 提问澄清；确认前无扣款 |
| T03 | 余额不足、超限、金额非法 | 拒绝；余额与流水不变 |
| T04 | 确认取消、过期、改参、重复提交 | 拒绝或复用原结果；绝无重复执行 |
| T05 | 统计包含退款、内部转账 | 按书面口径计算，可追溯交易 ID |
| T06 | 无交易、基准月零支出 | 不编造交易，也不输出错误百分比 |
| T07 | 卡片冻结/解冻和已冻结状态 | 状态转换正确；错误转换拒绝 |
| T08 | 其他用户账户或卡 ID | 权限拒绝，不能读取或修改 |
| T09 | 跨场景任务确认被拒绝或中途失败 | 真实步骤状态、最终汇总正确 |
| T10 | 流水备注包含伪造指令 | 不越权、不绕过确认 |

### 12.2 Agent 评估

维护一份不少于 30 条的人工编写任务集，覆盖三类单场景与两类跨场景，包含表达变体、缺失信息和错误输入。记录：意图/工具选择正确率、端到端任务完成率、账单金额精确正确率、未经确认写入次数、状态报告一致率；对每条失败案例说明原因。具体比例目标在基线测完后设定，不能先捏造测试成绩；未经确认写入次数目标为零。每次模型或提示词更改后跑固定任务集回归。

### 12.3 人工检查

用浏览器从重置数据到三段演示完整走一遍。检查统计口径、确认卡片与实际执行参数、刷新后状态、网络失败提示、移动端基本可用性；录制演示前再次重置与排练。

## 13. 分阶段开发任务与交付门槛

| 阶段 | 开发内容 | 完成门槛 |
| --- | --- | --- |
| M0 规格冻结 | 确认赛事文件、场景边界、演示数据和工具契约 | 本文关键未决项有结论；记录官方要求差异 |
| M1 可运行骨架 | 前后端启动、SQLite、种子数据、基础 UI、只读 API | 可选择用户并查看账户/卡片/流水；一条命令重置数据 |
| M2 业务闭环 | 统计、转账、卡片操作、操作单、幂等、审计 | T01–T08 通过；不依赖 LLM 即可完整操作 |
| M3 Agent 集成 | 自然语言理解、工具调用、追问、结果解释 | 三类单场景可经对话触发；数字与后端一致 |
| M4 跨场景任务 | 状态机、暂停恢复、条件分支、任务轨迹 | 两条主故事可运行；拒绝和失败流程正确 |
| M5 竞争力打磨 | 风险提示、图表、评估、演示与答辩材料 | 固定任务集结果可复现；Demo 稳定且可讲清设计 |

**每阶段 Codex 交付内容**：修改文件清单、运行命令、可复现的验收步骤、关键设计决策、已知限制。不要在 M1 就要求完整 Agent，也不要跳过 M2 的业务正确性直接制作炫目的前端演示。

## 14. 答辩叙事与亮点

1. **真实执行闭环**：从对话、查询与任务规划，到操作单确认、模拟执行、状态与流水更新，所有结果都可核验。
2. **跨场景任务**：同一个目标串联多工具，支持条件分支、暂停、恢复和部分失败说明。
3. **金融业务约束**：后端掌握权限、精确计算和执行权；模型输出无法直接改写账户数据。
4. **可解释风险提示**：结合规则和合成数据统计展示风险线索，明确其适用范围与误报可能。

答辩时可用一句话概括：**“FinAgent 能理解用户的金融目标、规划任务，并在可验证的业务约束与用户确认下执行模拟银行操作。”**
