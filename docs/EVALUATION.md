## 方法

40 条独立对话：账单 8、转账 10、卡片 8、跨场景 10、边界 4；开发 30、保留 10。严格 schema 检查分组、配额及 ID/完整对话去重。沿用 M5 定稿任务集及提示词，未依据本轮保留集调参。早期 M4 重复 holdout 不计为独立泛化证据。

每例固定种子与 2026-09-24，独立 SQLite；检查持久任务投影、末个活动工具、回复、指定步骤和金额/目标，以及 BusinessResult=0。全部是对话/准备层，按钮事件为空；不能以此替代写业务端到端通过率。

从任务创建到消息处理和断言结束计时，排除种子初始化，无真人确认等待。模型调用包含重试尝试；usage 只保存提供方返回的非负整数 token 字段，不存密钥、提示词或完整响应。费用无账单证据，实际费用为 null。表中 token 不含浏览器排练和流程实验。

## 表单与 Agent 流程对照

开发者用 Edge 自动化执行三项任务、每路径一次，每次重置隔离库；中间一项交替先后顺序。双方用同一页面和后端，表单不调用模型，Agent 为 live。每个 fill/select/click 计一次交互，不计初始化选用户、滚动或自动等待；核对实际数据库业务结果数、余额与卡状态。

| same-name-transfer | form | 7 | 0.249 | 通过 |
| same-name-transfer | agent | 5 | 2.662 | 通过 |
| unknown-purchase | agent | 3 | 4.115 | 通过 |
| unknown-purchase | form | 5 | 0.228 | 通过 |
| conditional-transfer | form | 8 | 0.263 | 通过 |
| conditional-transfer | agent | 3 | 4.589 | 通过 |

同名转账选择 3821；陌生消费从页面流水卡尾号核对，再冻结及查余额；表单条件转账先查询餐饮净消费，再手动填写转账。为支持手动核对，本阶段将流水已有卡关联显示为尾号。

每项 n=1，程序知道正确输入，没有人类阅读/思考时间。Agent 交互少、机器总耗时更长，不能推导用户效率提升。无外部参与者、理解评分或用户完成率；确认等待与理解评分为 null。表单条件判断依赖操作者，没有服务端固定条件复核，动态保护与 Agent 不等价。

原始记录 `evidence/m7/process-1790405643420.json`；复验 `scripts/compare-process.ps1 -Mode live`。初次启动脚本曾误引用不存在的夹具，业务未运行；修正后六次路径全部通过。此实验明确属于开发者自动化流程自测，不是用户研究。
